## S1 — Self-protection contract (0.02)

### S1.1 Trust, identities and protected set

TD §§2.1, 3.3 already forbid visibility and operations on Mandatary. Host/root/Docker-daemon compromise is outside the intermediary's protection boundary: an actor able to falsify the runtime identity and Docker inventory can bypass the intermediary entirely. Do not advertise protection against that actor.

- A runtime identity is a **full immutable container ID qualified by endpoint UUID**, not a container name, truncated hostname, image name, persisted previous ID, or a policy selector.
- Resolve supported evidence from the current process's runtime/cgroup identity and daemon metadata, an operator-provided exact `MANDATARY_SELF_CONTAINER_ID`, and `io.mandatary.self=true` labels. The explicit ID is an assertion by the trusted host operator, not an untrusted API input. Resolve the asserted full ID against the connected daemon; reject nonexistent IDs, partial IDs, unqualified names and endpoint mismatches. An explicit assertion conflicting with available process identity never wins by precedence.
- If cgroup/runtime evidence is unavailable on a supported host, use a host-provisioned per-instance binding: an instance UUID supplied to the process and the same UUID in a deployment-owned container label, alongside `io.mandatary.self=true`. Resolve exactly one current deployment member with that binding on the configured endpoint; compare any explicit self ID against it. This is trusted deployment metadata, not a policy/user-supplied selector, secret or new authentication provider. A fresh recreation may reuse the instance UUID only when the old member is gone; two extant matches are ambiguous and fail closed, including running/stopped overlap during recreation. Expected absence of a host-ID path under a private cgroup namespace is not contradictory evidence; an unreadable evidence source that configuration declares mandatory is a verification failure. This avoids pretending that an unqualified self label or truncated hostname proves process identity, and avoids a circular requirement to know Docker's future container ID before creating the container. The exact binding variable/label spelling is a Phase 1 implementation detail, documented and fixture-tested before P1.12 passes. If neither process evidence nor this trusted binding is available, remain unverified. A bare explicit ID is accepted only when validated against reliable current-process evidence/binding; host instructions must never reuse a stale ID blindly.
- Maintain a **protected set** containing the proven running instance and **all** containers with the self label on the relevant daemon. Inventory must explicitly include all states: created, running, paused, restarting, exited/stopped, removing and dead, not Docker's default running-only list. A stopped peer remains protected against start/inspect/log requests; a created or unhealthy peer remains protected too. Additional labelled containers broaden denial; they do not authorize anything. No ordinary policy administrator/API client can edit runtime identity, clear protection or insert an allow override.
- For multiple Mandatary instances (including the Phase 4 `--ops-only` instance), every deployment member must bear the self label. Each process must establish its own identity and protect the union of labelled peers, regardless of service name, principal permissions or UI listener. No arbitrary unlabelled application is assumed to be a peer merely because it uses a similarly named image. Validate the deployment membership contract before supporting the optional multi-instance layout.

### S1.2 State machine and failure handling

`UNVERIFIED -> VERIFIED -> UNVERIFIED` is an operational safety state, not a policy permission. Verification starts afresh on every process start, daemon reconnect, endpoint rebind or identity-relevant configuration change. Never restore `VERIFIED` from SQLite, a logical backup, previous container ID, or cache alone.

- **Missing identity:** startup may expose a generic liveness endpoint and restricted administrator diagnostics/recovery; Docker-backed readiness is false. Deny **all Docker-derived inventory, inspection, logs and mutations** until identity and protected-set discovery are verified. No partial unfiltered discovery or "just logs" fallback.
- **Ambiguous/conflicting identity:** multiple current-process candidates, mismatch between runtime and asserted ID, wrong endpoint, unreadable evidence or incomplete daemon inventory returns to `UNVERIFIED`. Deny all Docker-backed routes, including MCP and future operations UI, and cancel active Docker streams before reporting the state. A labelled peer set may legitimately contain many IDs; that alone is not ambiguous current-process identity.
- **Unavailable daemon/events:** a connection failure, uncertain inventory epoch or missed event continuity invalidates verification. Reconnect and resynchronize before resuming; cached permissions/IDs cannot authorize access during uncertainty. Service diagnostics do not embed protected IDs, Docker responses, tokens or stack traces in external errors.
- **Verified dispatch:** apply self-protection before policy. Recheck the target's current immutable ID and self label at the shared dispatch boundary; use that exact ID for the SDK call, never re-resolve a mutable name after authorization. Unknown target or failed safety checks deny without invoking the operation. A protected target is hidden from discovery and cannot be operated even with a wildcard allow or administrative role.
- **Container recreation:** the new process boots unverified and resolves its new ID. The prior ID does not prove the new process identity; stale assertions stop Docker-backed readiness until corrected. A stale protected ID may remain conservatively denied but never substitutes for current verification. A newly observed labelled peer is protected immediately; target-label checking prevents an event-cache lag from authorizing it.
- **Multiple instances:** concurrent instances independently verify and deny the same peer set. Loss of proof in one process blocks that process's Docker-backed surface; a different independently verified process is not forced to fail merely because the other process is unhealthy. Shared streams cannot continue on behalf of an unverified instance. Multi-instance coordination/storage does not bypass TD's SQLite concurrency or role boundaries and needs its Phase 4 deployment tests.
- **Mock development:** an explicitly selected mock backend must identify a synthetic protected fixture and apply the identical state machine. It is not evidence that production self-identification works and must never silently fall back to the real daemon.

Availability cost: Docker access is intentionally unavailable when safety cannot be established. Recovery is a trusted host configuration correction plus fresh verification, not an API override. This cost follows Nico's explicit fail-closed direction rather than changing the approved authorization model.

### S1.4 Approved native-development and real-Docker test boundary

Nico accepted the bounded disposition of TD §10.4's optional **native** macOS/Linux real-socket path. **Native mock mode is the guaranteed container-build-free local workflow**, including local unit/authorization tests. Real-Docker integration instead runs Mandatary as a containerized fixture that must establish the same self-proof as production. Optional native real-socket support is deferred until a separately reviewed trusted-native-runtime attestation contract is approved; it is not a required Phase 1 support target. Missing cgroup identity is not proof of native execution, and a native-mode switch never exempts a real backend from self-protection.

- **Practical isolation default:** a disposable dedicated test daemon in an isolated CI runner/VM, with separate daemon data, socket, networks and synthetic containers/credentials. Container names, Compose project labels or a separate network on a production daemon do not constitute daemon isolation. Provisioning that environment is future authorized test work, not a new production runtime service.
- The harness requires an explicitly selected fixture endpoint and checks its approved isolated-environment identity before setup or cleanup. Ambient `DOCKER_HOST`, default contexts and `/var/run/docker.sock` are never accepted implicitly. Nico's production Unraid socket/daemon must never be mounted, contacted or used for fixture creation/cleanup. Cleanup is bounded to the approved disposable environment; never use host-wide prune commands.
- If a dedicated disposable daemon cannot be provisioned on a developer machine, run native mocks there and use the authorized isolated CI environment for integration. Report unavailable integration evidence as **NOT RUN/blocked**, never substitute production access or weaken self-proof. Any alternative fixture topology requires independent isolation review before use.
- SELF-01–SELF-13, including all container states, recreation overlap, peer instances, reconnect and active-stream loss-of-proof, remain mandatory. Mock success is not proof of real-Docker behavior; native container-build-free iteration does not mean the separate containerized integration suite is build-free.

## S2 — Restore authority and rollback limits (0.06)

### S2.1 What authenticated backups do not prove

TD §6.3 HMAC/schema/envelope verification establishes provenance/integrity, **not freshness**. A valid old backup may predate a token revocation, account disable/delete, reduced group membership, removed allow, new deny, changed MFA policy or shortened expiry. Restoring that snapshot can restore historical authority even if sessions are dropped. Encryption/master-key possession does not make a revocation ledger monotonic; a ledger stored inside the same restorable SQLite file or copied volume can be rolled back with it. Reissuing agent tokens alone does not prevent old passwords/MFA, restored administrators, widened policies or future-dated temporary grants from regaining power.

Wall-clock expiry must use trustworthy current UTC, not backup `created_at` or a restored clock. Recompute every expiry at use; never convert remaining TTL at export into a fresh duration. If clock correctness is unknown, timed authority cannot be accepted; restore stays quarantined. Cryptographic signing timestamps alone do not prove current time.

### S2.2 Approved default: quarantine plus mandatory authority reactivation

**Nico approved this qualification of TD §6.3 full-restore activation semantics.** Keep full same-key import and clean/new-key import formats, transactionality and logical data scope. Import is not permission to activate imported authority.

1. Authenticate/authorize and step-up the live restore initiator **before** the availability-changing transition; a fresh-instance recovery requires trusted host authorization instead. Then stop/cancel all operations/streams and enter a persisted `RESTORE_QUARANTINE`. Invalidate existing browser sessions and bearer-credential acceptance, and rotate the live session/credential generation. On crash/restart quarantine persists. Archive content may never import/overwrite the live quarantine control flag, current credential/session generation, restore transaction lock, trusted recovery authorization or accepted security floor; those are local control-plane state outside the archive import mapping. Runtime self-protection must be independently reverified.
2. Verify archive schema/HMAC/envelope, parse into a staged transaction, perform structural checks and produce a redacted pre-commit change summary. No restored identity, MFA enrollment, endpoint credential, token hash, grant or policy becomes effective through staging, error paths or a racing request.
3. **Without a trustworthy external freshness/revocation authority:** all restored passwords/MFA/recovery codes and agent token hashes are inactive, including non-expiring service tokens. Require host-initiated one-time administrator recovery/re-enrollment, fresh user credential enrollment and fresh agent token issuance. Historical records can be retained encrypted for archive/provenance but must not pass verification. Reimporting backup hashes again cannot reset the current credential generation. Treat disabled/deleted-account history as unknown until explicitly reviewed; do not silently reactivate it.
4. Quarantine all restored positive authority **and security-relevant settings**: administrator assignments (still only one Phase 1 administrator), group memberships, ALLOW policies, temporary grants, endpoint credentials/connections, MFA/WebAuthn-only policy, enabled authentication/recovery paths, discovery exposure, password/credential issuance/expiry policy and later IdP/role mappings. Fresh enrollment uses the currently accepted security floor, not imported weaker settings. Retain deny restrictions conservatively while the host-authorized new administrator reviews a redacted authority manifest. Require explicit per-principal/role/membership/policy reapproval with new effective generation, not a global "trust everything in backup" checkbox. Phase 1 has no temporary grants; when introduced, never automatically revive them even if their old `expires_at` is in the future. Expired authority is never eligible for reapproval by copying old timestamps; a new grant is a distinct reviewed act.
5. Recovery-only enrollment authority is a separate narrow capability, not an AAL2 session or a container grant. After password + required MFA enrollment, authenticate normally before policy approval. Backup credentials cannot be used to approve their own reactivation. The trusted host operator explicitly establishes the recovery administrator; restored accounts cannot self-elect.
6. Resume ordinary access only after required credentials, policies, endpoint health and self-protection are verified and the authorized manifest is committed. A partially reviewed principal remains denied. Record a non-secret restore report/generation summary as Phase 1 operational evidence; the later Phase 3 administrative audit remains in its original phase.
7. Clean/new-key restore follows the same quarantine/reapproval flow and TD's mandatory credential re-enrollment. Same-key full import retains data fidelity but does not promise authentication continuity.

This approved restriction intentionally sacrifices automatic same-key credential continuity when current revocations cannot be known. It adds no database service or external dependency. Imported record fidelity and effective authority are distinct: explicit recovery/reissuance/reapproval establishes a new baseline, not a claim that unknown intervening revocations or DENYs were reconstructed. Host-authorized restore recovery uses the same protected host-local mechanism, shared control-state locking and restricted enrollment boundary as §S3; it cannot clear quarantine by editing database fields or reusing the initial-setup route.

### S2.3 Optional future continuity with trustworthy external revocation state

Not a Phase 1 architectural dependency and not permission to implement a new service. Automatic continuity would require an independently protected, current external authority covering **all** security-relevant generations/events: credentials, authenticator replacement, accounts/roles/membership, allow/deny changes, grant revoke/expiry and endpoint secrets. It must prove freshness/completeness and resist rollback relative to the restored host; a hash of the backup, restored file, same-volume tombstone table, stale signed checkpoint or operator memory is insufficient.

If that authority is unavailable, stale, inconsistent, unverifiable or missing any relevant history, **fall back to quarantine/reissuance/reapproval**, never optimistic preservation. Adding such an external dependency, selecting its trust model or promising rollback-resistant operation requires Nico's separate approval. A full host snapshot rolled back by a malicious host administrator cannot be detected reliably using only that same host's files/clock/keys. That is an explicit limitation, not a protection claim.

| RESTORE-02 | Backup before password/MFA/recovery-code change or account disable/delete; old credentials cannot log in, recover, enroll arbitrary factors or approve policy after restore. Reinstated admin/owner/group role remains inactive. |

### S2.5 Backup-scope boundary

R requires restart persistence of usage counts and a fresh-instance backup comparison against the **documented** scope, not an undocumented promise that every database table is exported. TD §6.3 explicitly lists policy/account/security records but does not list usage aggregates. Preserve that approved scope: fixtures compare included settings and effective authorization; usage rollups must survive ordinary restart but must not be advertised as recoverable from these backups. Document the exclusion clearly. Adding usage exports later requires an explicit scope amendment, not a fabricated restore result or a new Step 0 architectural blocker.

## S3 — Initial setup and emergency token contract (0.10)

### S3.1 Preserve setup flow; separate URL from secret

Preserve TD §10.3: empty-database bootstrap, a high-entropy single-use token, 30-minute lifetime, setup URL logged to stdout, administrator-supplied token, password and mandatory MFA before unlock. TD does **not require the secret to be embedded in the URL**. Log only a configured, validated **secret-free** setup URL (e.g. path `/setup`), never a token in query, fragment, path, request body log or HTTP redirect. No production URL is derived from an untrusted Host/forwarded header; only explicitly trusted proxy origin configuration is used.

**Approved disclosure:** a protected file and host-local interactive mode of the **existing static Mandatary binary**, not persistent container logging, an additional daemon, a new runtime technology or an interactive shell inside the distroless application. The following specifies future implementation and deployment documentation; no helper/command exists or has been exercised merely because it is described here.

- Generate at least 256 unpredictable bits using the OS CSPRNG. Persist only a token digest, purpose, target/installation identity, generation, issued/absolute-expiry timestamps, durable attempt/lockout controls, reveal state and consumed/revoked status in SQLite. A separate reveal file is the deliberate short-lived plaintext copy, with a 0700 parent and 0600 file owned by the actual non-root service UID/GID. Keep database/WAL/shared-memory and lock files equally restricted. Validate ownership against the trusted deployment's configured IDs, not merely whichever UID happens to own a preexisting file. Reject symlinks, unexpected hard links, unsafe ancestor directories, foreign ownership and group/world access; use descriptor-relative no-follow/exclusive operations inside the verified directory. No umask fallback or recursive permissive chmod.
- Never put plaintext in environment variables, argv, repository files, application/logging output, telemetry or logical backups. Transient reveal files are explicitly outside Mandatary's backup export mapping; host backup operators must exclude/protect them too. Arbitrary host snapshots and terminal recording are outside the intermediary's protection guarantee. Cleanup is logical unlink, not a promise of forensic erasure from storage/snapshots.
- The logged URL is public routing information; the administrator manually supplies the revealed token in an HTTPS form. Submit via POST over the configured protected channel with CSRF/origin defenses. Set no-store and no-referrer headers and do not install third-party scripts/assets on setup. Requests/responses, reverse-proxy access/error logs, browser history, analytics, traces and test artifacts must not contain token plaintext. Automated tests use synthetic token values.
- Enforce the original absolute **30-minute** lifetime against trustworthy current UTC; restart/retry/retrieval does not extend it. Expiry/revocation/consumption makes any leftover file unusable immediately and schedules protected cleanup. Never mint a fresh token automatically on restart or re-enter setup on missing/corrupt/migration-error state. Clock uncertainty denies issuance, reveal and exchange; changing host time to regain a window is not recovery.
- First valid token POST atomically binds it to **one** setup-only server-side session, marks the token consumed and rotates the session identifier. Racing/replayed submissions fail. The session expires no later than the original token's expiry; exchange immediately before expiry does not extend enrollment time. Failed guesses use shared durable counters/backoff and bounded attempts under the approved authentication policy, not restart-resettable in-memory buckets alone. No error echoes a supplied token or reveals account existence.
- A setup-only session establishes only the first administrator's password and required MFA, with proof of authenticator control. It has no policy, container, backup or ordinary login authority and never carries an AAL2 label. Only committed enrollment and subsequent qualifying authentication unlock ordinary administration. If an initial administrator has committed, setup handlers and every outstanding initial token/session are disabled atomically. No URL GET mutates setup.

#### S3.1a Shared reveal/consume/rotation and crash protocol

**One coordination domain:** every application process and host-local helper opening this installation uses the **same persistent on-volume lock inode and the same existing SQLite control records**, through the same storage/control-transition implementation. An in-process mutex, host-only PID file or separately copied SQLite database is insufficient. Take the OS advisory lock first, then a SQLite write transaction; no code path may take these in reverse order. Validate that host/container paths resolve to the same mounted directory/database/lock identity. Never unlink/recreate the lock file while it is in use. Require a local filesystem with tested SQLite WAL, shared-memory and cross-process lock/sync semantics; network shares or unverified mount aliases are not supported by this workflow. SQLite WAL's shared-memory model requires same-host participating processes.[2] SQLite's own interprocess writer locking remains necessary; a single-writer pool only coordinates one process. Lock/database busy, identity mismatch or I/O failure fails closed with a redacted error, not an unlocked fallback.

**Durable-before-disclosure:** TD's general `synchronous=NORMAL` is not sufficient evidence of power-loss durability: SQLite explicitly distinguishes process-crash survival from WAL commits that may roll back on power loss/system crash.[1] Security-control transactions in **both** helper and service use a verified `synchronous=FULL` WAL writer connection, with required file/directory syncs, before any secret delivery or acknowledgement dependent on that state. This is a narrowly scoped durability refinement using the selected SQLite stack, not a new store/service or a claim that every usage-counter write is power-loss durable. Sync/commit failure denies; host/filesystem/hardware honoring sync remains a trust assumption. These control records and generations are non-importable under §S2.

| Transition | Required ordering under the shared lock |
| --- | --- |
| Issue / explicit rotation | Revoke the previous generation and its enrollment sessions durably; create a new non-revealable `PENDING` digest record with absolute expiry. Create and sync the generation-bound 0600 plaintext file atomically, then durably set `AVAILABLE`. Release only after directory sync and consistent state. A database/file step failure or crash leaves `PENDING`/orphan state unusable; clean it under the lock and require explicit host rotation, never complete/reissue implicitly on restart. Existing administrator/restore/recovery-purpose checks apply before issuance. |
| Reveal | Before accessing plaintext, require matching build/schema/installation/UID, a real controlling terminal with unredirected stdin/stdout/stderr, `AVAILABLE`, current generation, valid purpose and unexpired UTC. Durably change reveal state to `CLAIMED` **before** terminal output. Keep the shared lock through the final expiry/generation check, bounded terminal write, unlink and directory sync; then durably record `RETRIEVED`. The secret bypasses `slog` and is written only to that terminal. File retrieval is not HTTP token consumption. |
| Crash / failed reveal | A persisted `CLAIMED` or failed/uncertain terminal write is never revealable again, even if a plaintext file survives. Conservatively invalidate the token generation and enrollment session under the lock and remove residual plaintext on restart/reconciliation; require explicit host rotation. Crash after output but before cleanup is uncertain human receipt, not exactly-once delivery. If cleanup/state persistence fails, retain non-revealable status and block exchange until consistent recovery. A refused pipe/redirection before claiming emits no secret and does not pretend to have delivered one. |
| Token POST / failed attempt | Under the same lock, check purpose/generation/expiry/reveal-state/attempt controls, verify the digest, and atomically commit consumption plus one restricted session, or the failed-attempt update. An HTTP exchange may accept only a consistent `RETRIEVED` generation, never `PENDING`, `AVAILABLE`, `CLAIMED`, invalid/expired/consumed state. Remove residual plaintext before reporting success. A crash after commit does not replay consumption or create a second session; lost session delivery needs explicit host rotation, not token reuse. |
| Expiry / enrollment commit / restore / rotation | Share the same lock and durable generation/session invalidation. No worker may copy a secret under the lock and output it after releasing the lock. Recheck UTC immediately before reveal/exchange; expiry cannot be delayed merely because a cleanup worker is waiting. Enrollment commits only if its original absolute expiry still holds. Restore invalidates outstanding reveal/enrollment authority before import; archive data cannot reset it. Restart reconciles state before enabling relevant handlers. |

A terminal write cannot promise the exact instant a human receives bytes; a stalled/partial write is uncertain delivery and triggers the fail-closed rule, not an extended lifetime. No lock lease or automatic stale-claim timeout can make `CLAIMED` revealable. Lost/expired setup-only sessions, incomplete enrollment and uncertain delivery require explicit trusted-host rotation/recovery; they cannot mint replacement authority automatically.

#### S3.1b Host-local deployment runbook — Compose and Unraid

P1.09 delivers these subcommands in the existing Go binary; P1.19 delivers the matching host artifact, deployment manifest and exact invocation reference. **Command purposes below are design interfaces, not assertions that today's repository implements them.** The host helper never starts the server, discovers Docker containers, opens a Docker socket, migrates/creates a missing store, edits policy, or supplies a native-runtime self-proof exemption. It opens the existing verified store only for the narrow security-control transitions above. This remains a single production application binary/image; invoking another short-lived copy of that binary does not add a service. Distroless's deliberately absent shell/package manager is why the supported procedure runs this existing binary on the host rather than requiring an application-container shell.[5]

1. **Prepare the trusted host entry point before first startup.** Use the matching Linux CPU/version static Mandatary artifact from the verified release, with the same hash/build as the deployed image's binary, installed in an administrator-owned, non-group/world-writable host path. P1.19 must publish the artifact/hash relationship and supported host execution evidence; an arbitrary downloaded helper or mismatched binary is refused. No Go installation, package manager, debug image, shell inside the application or always-on helper is required. A replacement binary after upgrade must match before it opens the store; the helper does not auto-upgrade a schema.
2. **Record actual paths and numeric ownership.** The trusted deployment manifest identifies the installation, mounted data-directory source, actual configured container UID/GID, corresponding host UID/GID (including any user-namespace mapping), master-key file location when needed for the narrow operation, and binary/schema version. Run the helper as that mapped host identity. If the trusted host administrator launches it as root, the helper must explicitly drop supplementary groups and set the configured service GID/UID before opening data/secret files, then verify the drop. It must not run as UID 0 or remain root while reading the token. Unsupported ID mapping fails with instructions for the host administrator, never chmod/chown-to-match based on untrusted files. Docker-socket access groups must not thereby gain read access to the token directory.
3. **Compose:** the shipped host-local workflow uses a dedicated persistent **local bind mount** with its exact host-to-`MANDATARY_DATA_DIR` mapping and UID/GID preparation documented before startup, not the image root or an assumed working-directory copy. This concretizes the already required data volume, not a new storage service; Docker recommends bind mounts when host and container both need file access.[3] Host helper and application open that same mounted directory; do not copy the database/reveal file elsewhere. A Docker-managed named volume is not implicitly supported for host-helper access: do not manipulate Docker's private backing path. Such a layout needs a separately documented, tested supported access route before it can be offered with this retrieval workflow; otherwise use the documented bind mount without relaxing permissions.
4. **Unraid:** use the actual host-local appdata source mapped to the application's data directory, recorded from the installed template/configuration; do not assume a universal share path, UID/GID or that `PUID`/`PGID` variables automatically change the distroless process user. The host administrator provisions owner-only access for the actual mapped service identity and verifies local backing-store lock/WAL behavior. Exclude the protected directory from ordinary SMB/NFS sharing and broad share-permission repair jobs; refuse retrieval if access has been widened. The same verified Linux binary runs on the host from an interactive local or authenticated SSH terminal; Unraid's in-container console/shell is not used. This describes required future Unraid runbook validation, not blanket tested support for an unspecified Unraid version.
5. **Retrieve and enroll.** After empty-store startup, read only the secret-free setup URL from logs. On the trusted host, invoke the helper's **initial-setup reveal** purpose with the recorded existing data directory and mapped UID/GID; a root launch requires explicit target IDs. It verifies the host-side terminal before opening plaintext and follows §S3.1a. No secret is passed as an argument. Do not use `cat`, shell substitution, clipboard automation, pipes, redirection, Docker log output, CI output or an in-container shell. Paste manually into the protected setup form, choose a compliant password, prove mandatory MFA, then perform a normal qualifying login. A web administrator's application role alone never grants host-file/reveal access.
6. **Expire, fail or lose the session:** invoke the helper's explicit **initial-setup rotate** purpose only while no administrator exists; it invalidates the old token/session and starts a new absolute 30-minute generation. Existing-admin emergency recovery uses **reset-MFA for a specified existing user**, never initial setup; restore-quarantine recovery uses the separate **restore-administrator recovery** purpose and cannot approve imported authority. Each issuance/reveal uses the same protected file, actual-terminal and shared-state protocol. Redacted status can report purpose/generation/expiry/outcome but never the secret/digest. Missing key/store, uncertain clock, unsafe mount/permissions or mismatched build is an operator-visible blocker; do not clear state by hand, erase the store or disable MFA.

The final command spelling, artifact paths and mount/UID values must be concrete in the shipped P1.09/P1.19 runbooks and exercised by SETUP-11/12 before either deployment is supported. They are deliberately not invented as executable commands in this pre-implementation contract. A future **direct non-shell binary subcommand** invoked by a host administrator through the container runtime may also be documented, but must preserve host-side terminal checks and the same coordination/durability semantics; allocating a container TTY alone is not proof that the host has not redirected output. It is not a fallback permission to execute a shell or expose secrets in runtime logs.

**Trust limit:** root, the service UID, deployment/Docker administrators able to change mounts or run commands as that UID, and the host terminal are trusted. File modes prevent ordinary users/log readers from learning the token, not these actors. Changing data paths, lock files, keys, time or executable code maliciously is host compromise, not a boundary this design claims to defeat. The host helper's narrow implementation prevents an application administrator from using the web/API to invoke host recovery; it cannot constrain a malicious host administrator.

### S3.2 Emergency recovery

TD's host-invoked recovery command remains an approved **product capability**, not authorization to execute containers in this task. Use §S3.1b's host-local same-binary entry point and §S3.1a's shared durable reveal/consume protocol. Emergency MFA-reset tokens have a separate purpose/record from initial setup and restore recovery, the same unpredictable/one-use/30-minute-or-less absolute expiry, and one specified existing-account binding. Durably invalidate affected sessions, old recovery capabilities and credential generations before issuance; successful exchange grants only required credential replacement/re-enrollment. It never becomes an ordinary session by itself, clears restore quarantine, or approves imported authority. The sole Phase 1 administrator can recover through trusted host authorization without a second application administrator; an ordinary web/API administrator role cannot invoke host recovery.

Normal recovery methods and their assurance boundaries follow NIST map D-04. **All-factors-lost host recovery is an application-specific trusted-host procedure, not a claim of NIST AAL2 recovery or identity proofing.** Require the documented operator risk acknowledgement, independent security notice, proof of the newly bound policy-required MFA and fresh qualifying normal authentication before administration. Password replacement, if required, happens only within that restricted ceremony. Recovery cannot quietly erase WebAuthn-only policy, revive old credentials or satisfy AAL2 with a recovery bearer alone. Notifications/binding evidence and delivery-failure handling follow `nist-authentication-mapping.md`; no unauthenticated reset endpoint or silent MFA-disable fallback is added.
