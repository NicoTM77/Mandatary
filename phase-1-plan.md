# Mandatary — conditional Phase 1 Kanban proposal

## Authorization and ownership

Nico provisionally approved the P1.01–P1.20 structure on 2026-10-26, subject to Step 0 completion and final backlog review. This is a **proposal, not an executable queue**. Do not create dispatchable implementation cards or start coding until Step 0 exit criteria are met and Nico explicitly approves Phase 1. Use existing project/board `mandatary`; never recreate the completed workflow-validation task or the existing Step 0 cards.

All implementation cards below are assigned to **`coder`**. Each must hand off with native `kanban_request_review(reviewer="reviewer")`; `reviewer` independently inspects the exact commit, tests, security boundaries and deliverables before closure. A dependent task must wait for the predecessor's reviewed completion and Nico-controlled merge of the prerequisite PR, unless Nico explicitly authorizes a stacked-PR workflow. Neither worker nor reviewer may merge, enable auto-merge/merge queues, or reinterpret a review approval as merge permission. Use project-managed worktrees and feature branches. GitHub operations use `/opt/data/integrations/github/bin/axiom-github gh` and existing git credentials. Draft PRs only; no merge, deployment or authentication integration changes. Preserve `HERMES_WRITE_SAFE_ROOT`; scratch files belong in `/opt/data/scratch/`.

References below: **R** = `roadmap.md`; **TD** = `technical-decisions.md`. All tasks inherit R shared release criteria. No task may resolve an open architectural conflict unilaterally. The baseline's explicit permitted implementation alternatives do not authorize a different stack.

## Conditional amendments surfaced by the completed standards review

These are **not approved phase-boundary changes**. The 20-key structure remains provisional; affected cards cannot be finalized until Nico disposes of the decisions in `nist-authentication-mapping.md` and `security-contracts.md`.

- **N1 — minimal Phase 1 security notifications (approval required):** recommend moving only the security-event subset of the existing planned SMTP capability forward: independent authenticator-binding/recovery/recovery-code notices, support for at least two notification addresses, verified address changes, redacted durable delivery state/retry/failure visibility and safe event repudiation. Agent access requests, approvals, discovery, webhooks and their UI remain Phase 2. No provider or additional service is selected. If approved, add address/outbox schema tests to P1.02, lifecycle hooks/delivery tests to P1.06–09, address/setup/recovery UI to P1.16 and isolated SMTP receiver/TLS/failure fixtures to P1.19/20. C2/C3 then require the applicable N63B4 notification tests. If not approved, do not claim full AAL2 satisfaction; Nico must explicitly decide the assurance/release requirement conflict.
- **N2 — password and retry invariants:** propose 15 characters whenever a password can authenticate alone; permit 8–14 only while MFA is enforced with no weaker fallback. Retain five-failure throttling and propose a durable ceiling of 100 consecutive failed authenticator attempts, then disable/rebind. P1.02/05/06/08/16 own state/transition/concurrency/restore tests. These clarify missing normative controls without imposing MFA on all users, but D-02/D-05 need explicit disposition before acceptance.
- **R1 — recovery/restore:** security-contracts.md §S2 proposes quarantine, current control generations and mandatory credential reissuance plus explicit authority/security-setting reapproval when trustworthy external revocation state is absent. §S3 proposes host-local one-time secret reveal and a secret-free logged URL. Preserve backup formats and first-admin MFA flow; Nico must accept the changed continuity/disclosure semantics before P1.09/P1.18 acceptance. No external revocation service is added.
- **D1 — support/deployment:** support-and-deployment-matrix.md supplies exact candidate pins and support/test matrix. A current-maintained distroless Debian13 base is recommended because the approved Debian12 tag is no longer updated upstream; no Dockerfile may adopt that tag change without Nico's approval. Native real-socket development remains a separate fail-closed identity conflict (§S1.4), not an automatic exception.
- **A1 — assurance boundaries:** Nico's explicit direction settles session-/path-scoped assurance. Every N63B4 test is a future implementation obligation; the completed mapping is not implementation conformance. Agent bearer tokens, preauthentication, setup and recovery-only capabilities never become human AAL2 sessions. Governance/provider/cryptographic recommendation evidence is reviewed in its owning task rather than inferred from library names.

## Continuous checks and independent review — applies to every implementation PR

1. **P1.01 establishes working CI, not a final-phase promise.** Run Go formatting/build/vet/race tests and the security/authorization fixture suite, frontend locked install/typecheck/lint/tests, `govulncheck`, `gosec`, `golangci-lint`, and dependency advisory checks from the first PR containing the relevant ecosystem. Lock Go modules/tool versions and npm dependency graph; use `npm ci`, not unlocked latest installs. A check without a target may be explicitly not-applicable with a reason until its owning task exists; it is never reported as a successful scan of nonexistent code.
2. New authentication, authorization, persistence, Docker/mock or browser surfaces ship with positive **and negative** tests in the same PR; no intermediate publicly callable surface bypasses authentication, assurance, quarantine or the authorizer. P1.02 tests structural denials, P1.03 tests persisted inactive authority/tamper, P1.04 tests redaction, P1.05–10 continuously accumulate the NIST mapping tests. P1.11 can run in parallel with login work because it consumes explicit credential-status interfaces and fixtures, not an unfinished UI. P1.13 cannot become callable until real credential/session status is integrated.
3. Every code PR runs **all existing** security/authorization regressions, not only tests inferred from changed paths. Record the test command, fixture/matrix IDs, exact commit and results. From P1.14, API/MCP integration runs on every relevant PR and at each checkpoint; from P1.16 add browser flows. Once P1.19 creates an image, scan it with the TD Trivy gate and build both supported CPU targets on relevant PRs; platform-isolated runtime tests remain distinct from cross-compilation.
4. Required checks include a genuine nonempty test suite and build, no unknown/skipped check treated as green, and no reachable unresolved High/Critical or failing negative-authorization case. Scanner findings need reachability/disposition evidence and independent review, never a blanket allowlist or silent severity downgrade. Tool/advisory failures are fail-closed for the affected PR gate; proposed exception goes to Nico, not the implementer.
5. `reviewer` independently inspects the **exact head SHA**, performs appropriate targeted tests, checks CI itself and records a verdict, required fixes and residual risks. New commits invalidate prior exact-head review; rerun relevant CI and review. `coder` cannot self-review or complete work by claiming reviewer approval. Where a shared GitHub App cannot submit a formal approval of its own PR, record the independent worker's signed-off report/comment honestly; do not impersonate another account or count it as GitHub-enforced human approval. Nico retains final GitHub approval/merge authority.
6. Handoff requires a draft PR, implementation/test artifacts, negative-case evidence, updated contract-to-test links and no unresolved release-blocking review finding. Native `reviewer` handoff governs task review; dependencies additionally wait for Nico's merge unless he authorizes stacking. Do not configure protection settings, auto-merge, automated decomposition or dispatch as part of this documentation work. Green CI and review are **necessary, not permission to merge**.
