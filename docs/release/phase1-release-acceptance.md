### F1 / F2 of review 519 - Hosted run 44003552068 at e5e1856: REST 502 on X-dn-stop-A, and the server write bound that cut off long stop/restart calls

* **Adverse run:** hosted CI run 44003552068, job `Image (linux/amd64)` (head e5e1856, merge commit 0d6b022fc1d1b180092ac87fd2409a0c85422b3e): `REL-MATRIX-REST`, `REL-MATRIX-PARITY` and `REL-MATRIX-POS` FAIL, X-dn-stop-A: REST `(502, '', '')`, MCP 200. Archive root `adverse-ci-e5e1856/`; the run was omitted from the first version of this evidence (review 519 F1) and is now recorded as an adverse run of the criteria that cite those checks.
* **Finding and cause:** Review 519 reproduced a product defect on the same call shape: `cmd/mandatary` set a 10 s `WriteTimeout` on every response while an admitted one-shot stop or restart may run `timeout_seconds` plus a 15 s stop grace (10 + 15 s by default, up to 315 s). The server closed the connection before the handler wrote its result, so the client saw EOF (behind the proxy an empty-body 502) although the stop completed and was counted allowed. The harness then recorded no per-call timing, so it cannot be shown from the archived run that its X-dn-stop-A call exceeded 10 s.
* **Fix:** Narrow, after authorization only: the ops service announces the dispatch bound of an admitted stop/restart (`ops.DispatchObserver`, only for those two operations, only after authorization and the expired-bound check); the REST and MCP transports then extend that one response's write deadline to bound plus 5 s (`api.WithAdmissionDeadline`, forward only, read deadline untouched). Unauthenticated, denied and invalid requests keep the 10 s bound. No authorization, identity, invalidation, lease or freshness semantics changed. Documented in docs/api-mcp.md and docs/operations.md.
* **Regression tests:** RED-to-GREEN through the real `serverFor`, REST and a real MCP client against a slow executor (`cmd/mandatary/stop_write_deadline_test.go`: an admitted stop and restart deliver their result past the 10 s bound; unadmitted requests keep it), the ops observer tests (`internal/ops/dispatch_observer_test.go`: announced only after authorization and only for stop/restart), the transport unit test (`internal/api/admission_deadline_test.go`), and hand/script mutation checks of the wiring. The release harness gained per-call REST/MCP timing in the matrix stage and the `REL-STOP-LONG` check (container A ignores SIGTERM, `timeout_seconds` 12: REST stop, start and the MCP restart must still answer 200 although they outlast the 10 s bound, and A must run again; an unmeasured or fast answer is a failure); its fail-closed behaviour has positive and eight negative unit twins (`tests/release/test_release.py`).
* **Fresh evidence:** At the code commit 2ac064f: the VM run (`vm-amd64`) 156 PASS / 0 not PASS and both hosted CPUs (`ci-amd64`, `ci-arm64`, hosted run 44059883746) 156 PASS / 0 not PASS: `REL-MATRIX-REST`, `REL-MATRIX-PARITY`, `REL-MATRIX-POS` and `REL-STOP-LONG` PASS on all three (the REST stop answered 200 after 12.2 s on every CPU). * **Not established:** that the write bound was the cause of the one hosted 502: the archived run has no per-call timing and the failure did not recur (the hosted runs 44044826495 at 45629a3, 44055078430 at 41ae8d5 and 44059883746 at 2ac064f all passed `REL-MATRIX-REST`), so the cause of that single 502 is not established. ### F-2 - Start-up transient: about 100 MB resident for 2.5 minutes after every start

technical-decisions.md 10.2 states the idle budget as "after startup" without a duration. In steady state the service is well inside it (27.8 MB after a first start, 33.3 MB when configured, 27.2 MB after a restart; `vm-amd64/release.json`, `footprint.idle`), and `REL-FOOT-SETTLE-*` passes. But every start (first start, restart, SIGKILL restart) first holds about 100 MB (100.55 MB peak after the first start, 98.81 MB after a restart) until 145-155 s, i.e. roughly twice the budget for two and a half minutes; the same figures were measured on both hosted CPUs (98-99 MB, settled at 140-160 s). It reproduces natively with the container's environment: with the SMTP relay configured, one heap allocation of about 64 MiB happens 85 ms after start (`GODEBUG=gctrace=1`: `94->94->88 MB`), and Go returns it to the OS only after the runtime's 2-minute forced collection. Not asserted here: which code path allocates it. A follow-up in the product (release the memory after the one-time work) would remove the transient; the harness records the whole curve and gates on the settle. R3 (owner decision): the steady-state definition of the idle budget (the maximum of the samples inside the final 60 s of a 300 s window) is accepted and documented in docs/release-acceptance.md; the transient itself is still reported (`REL-FOOT-SETTLE-*`).
