### F-1 - TestSecurityUIBrowser/recovery-reveal-phone fails on Firefox (SH-9a FAIL)

`browsers/firefox-desktop.log` and `browsers/firefox-phone.log`: `TestSecurityUIBrowser/firefox/recovery-reveal-phone/{light,dark}` fail with `replacement code: Hide the code button is below the fold after focus (... ### F-2 - Start-up transient: about 100 MB resident for 2.5 minutes after every start

technical-decisions.md 10.2 states the idle budget as "after startup" without a duration. In steady state the service is well inside it (27.8 MB after a first start, 33.3 MB when configured, 27.2 MB after a restart; `vm-amd64/release.json`, `footprint.idle`), and `REL-FOOT-SETTLE-*` passes. But every start (first start, restart, SIGKILL restart) first holds about 100 MB (100.55 MB peak after the first start, 98.81 MB after a restart) until 145-155 s, i.e. roughly twice the budget for two and a half minutes; the same figures were measured on both hosted CPUs (98-99 MB, settled at 140-160 s). It reproduces natively with the container's environment: with the SMTP relay configured, one heap allocation of about 64 MiB happens 85 ms after start (`GODEBUG=gctrace=1`: `94->94->88 MB`), and Go returns it to the OS only after the runtime's 2-minute forced collection. Not asserted here: which code path allocates it. A follow-up in the product (release the memory after the one-time work) would remove the transient; the harness records the whole curve and gates on the settle.
