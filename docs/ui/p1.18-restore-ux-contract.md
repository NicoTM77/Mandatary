# P1.18 export, restore and reapproval UX contract and presentational baseline (P1.18.2)

Contribution P1.18.2 (`t_48695952`) to P1.18 (`t_d57c6741`). This page is the design and state contract the
P1.18.3 containers (HTTP, step-up, file handling, routing) build against. It is a **design contract and a
presentational baseline, not working recovery**. Nothing here is a NIST, FIPS, accessibility-conformance,
browser-support or product claim. Every state labelled *synthetic* is an illustration, and every assumption in §9
must be validated by the coder against the real services.

Source of truth for behaviour is [docs/backup-restore.md](../backup-restore.md) (P1.18.1: authority model, archive
checks, the two restore transactions, the reapproval rules, the HTTP contract and its §7 safety table). This page only
decides how that contract is *presented*. Where a screen needs something the service does not expose, §8 lists it as an
open item, never as an existing API.

## 2. What the screens say in words (and never enforce in code)

1. **Nothing in the UI is authority.** A hidden link, a missing checkbox or a disabled button is presentation. Every
   request is validated by the service; a page shown to the wrong person exposes nothing. `Load.denied` renders the one
   refusal that does not say why (not the administrator / no second factor / authority changed).
2. **A backup is a snapshot, not a rollback.** `SnapshotNote` is on the export and restore pages and cannot be collapsed:
   *"It lists who and what is configured at the moment it is made. Restoring it does not undo later changes, and the file
   does not record what was revoked or when."* No copy anywhere says "roll back", "restore point", "revocation history" or
   "undo the restore" (`RecoveryGallery.test.tsx` asserts it over every state).
3. **Neither backup type brings a credential back to life.** Same-key (**full**) archives carry sealed sign-in and token
   records that are kept *switched off for reference* and can never be reactivated; **clean** archives carry none. Every
   page where it matters says people set up sign-in methods again and agents get new tokens.
4. **A restore ends the session and closes sign-in.** Said before the file is chosen, again inside the typed confirmation,
   and again on the result page. Only the host can end quarantine; the pages never offer a way to.
5. **Approval is explicit and per record.** No select-all, no default selection, no "approve everything" (the service has
   no such operation). One request carries the *named* records; it is all-or-nothing.
6. **Imported-versus-effective appears only where the service exposes both** (§4.3): a user's second-factor requirement and a
   rule's Allow/Deny. Every other record shows no comparison rather than an invented one. There is no preview of an archive,
   because the service has none; the restore page says so and states what is checked server-side.
7. **Secrets stay out.** The contract has no field for archive content, a verifier, a token or a key. The screen sees the
   browser's `File` handle (name and size) and hands it to the container. `source.test.ts` asserts the contract and the
   screens contain no cryptography, no file read, no JSON parse/stringify, no object-URL and no navigation.

## 3. Design language and Apple principles, adapted for the web

Reuses P1.16's shell, tokens and motion unchanged. Both themes come from the semantic tokens: `source.test.ts` fails on any
`dark:` variant, raw colour or inline style in these sources, and the structural audit (§6) ran in both themes.

* **Clarity through sequence, not decoration.** The restore page reads top to bottom as the person decides: what a restore
  does (six consequences, each a bold lead and one plain sentence) → choose a file → typed confirmation. Deference: the
  consequences are a quiet divided list, not a wall of warnings; the danger tone is spent once, on the confirmation panel.
* **Friction proportional to consequence.** Export is one decision (two radios, the choice named on the button). Restore is
  gated by the step-up, the typed phrase `RESTORE`, and (only when the service says the origin is unverifiable) an
  acknowledgement. Reapproval is checkbox + named confirmation. The extra steps appear where the *irreversible* effect is,
  not everywhere. This is the HIG's "confirm the destructive action, name what it affects" translated to an inline
  `ConfirmPanel` (D-CONFIRM-1), never a modal.
* **The acknowledgement is an answer, not a habit.** There is no preview API, so the page cannot know a file's provenance
  in advance. The first attempt always sends `acknowledge_unauthenticated_provenance: false`; only a 409
  `provenance_unverified` makes the checkbox appear, with that finding next to it. The box starts unticked, is never
  remembered, and the file is re-sent on the next press. (An always-visible box would be ticked by reflex.)
* **Terminal states are pages, not toasts.** After a restore the session is gone. The three outcomes that follow
  (`complete`, `incomplete`, `unconfirmed`) render as a pre-session page with one numbered next-step list, no retry button
  and focus on the headline alert.
* **State is never colour alone.** Every badge and alert pairs an icon with text; Allow/Deny differ by word *and* icon; the
  "applied when approved" box that differs from the file is warn-toned **and** carries a written sentence.
* **Native controls only** (`RadioGroup`, `CheckboxField`, `<input type="file">`, `TextField`): keyboard, screen-reader and
  autofill behaviour are the browser's. The file input is styled with `file:` utilities from tokens.
* **Plain voice.** Sentence case, active verbs, an action keeps its name through the flow ("Export clean backup" → "Backup
  file created"; "Restore this backup" → "Restoring…" → "Restore complete"; "Approve 3 records" → "Approved 3 records").
  Errors say what happened, whether anything changed, and what to do. They never apologise and never reflect the failing
  check (the service sends fixed classes).

## 4. Screens and states

All three are stateless functions of `(state, data, callbacks)`. Local state is only what a form owns: the export mode, the
chosen `File` handle, whether a confirmation is open, the typed phrase and acknowledgement, and the ticked records. **None of
it is secret.** `initialMode` / `initial` props exist so the gallery and tests can show mid-flow states; a container never
passes them.

### 4.1 Export (`ExportScreen`, route `/backup`)

`{ state: ExportState, onExport(mode), initialMode? }`. Clean is the default.

| `state` | Presentation |
| --- | --- |
| `idle` | Two radios, each with its consequence beside it; "Both types hold / Neither type holds / Only a full backup holds" in text; the button names the choice ("Export clean backup"); a note that a recent verification is needed |
| `idle` + full selected | adds the *"A full backup holds credential material"* warning (sealed with this installation's key, not in the file; store it as a secret) |
| `working` | button busy (`aria-busy`, stays focusable, ignores repeats), radios locked |
| `done` | success `Alert`, focus on it: the file name, backup id, mode-specific storage advice, *"Nothing in this installation changed."* |
| `rejected` | `denied` / `invalid_request` / `rate_limited` / `unavailable`, each "Nothing was exported"; the form stays usable. Export is read-only, so **every** failure is safe to retry |

### 4.2 Restore (`RestoreScreen`, route `/restore`; `RestoreEndedPage`, no route of its own)

`RestoreScreen`: `{ state: RestoreFormState, onRestore({ file, acknowledgeUnauthenticatedProvenance }), initial? }`.

Flow: *what a restore does* → *choose the file* (name and size only; empty and >16 MiB refused locally with a plain message,
focus on the field) → **Restore from this file…** opens the typed confirmation → type `RESTORE` → **Restore this backup**.
The opening button stays on the page while the confirmation is open so Escape and Cancel can return focus to it.

| `state` | Presentation |
| --- | --- |
| `idle` | as above |
| `working` | confirmation busy; `role=status` "Restoring. This can take a minute. Don't close this page, go back or reload it."; phrase read-only, file input and Cancel disabled; Escape ignored |
| `needs_acknowledgement` | warn alert (focus) *"This file's origin can't be verified. Nothing was changed."*; the open confirmation gains the unticked checkbox; the typed phrase is kept |
| `rejected` | danger alert (focus), confirmation closed, file kept so the person can retry or choose another; **every** reason says "Nothing was changed" and none mentions quarantine |

Rejection reasons (`archive_*` are the 422 codes): `archive_malformed`, `archive_unsupported_version`,
`archive_integrity_failed` (covers a modified file **and** a full backup from another key, and says it can't tell which, and
points to a clean backup for moving installations), `archive_inconsistent` (authentic but self-contradictory),
`invalid_request`, `denied`, `rate_limited`, `unavailable`.

`RestoreEndedView` / `RestoreEndedPage` (`CenteredFrame`, **not** the signed-in shell): `{ ended: RestoreEnded, runbookHref?, signInHref?, onReload? }`.

| `ended` | Headline | What the page commits to |
| --- | --- | --- |
| `complete` | "Restore complete" · *Sign-in is closed until the host recovery is done* | counts only (imported, already-here-kept, credentials kept inactive, what was not read); origin; next steps 1-4 (host recovery → sign in → review and approve → set up credentials again); a calm note if `authorizerNotified` is false |
| `incomplete` (`failed`) | "The restore didn't finish" · *Sign-in is closed, and nothing was imported* | the first step had happened (sessions ended, sign-in closed); the same file can be restored again after the host recovery, and that is safe |
| `incomplete` (`superseded`) | same | names the competing restore and says to look at what it imported before restoring again |
| `unconfirmed` | "Mandatary couldn't confirm what happened" · *Don't start another restore yet* | **no claim either way**; how to find out (reload: still signed in ⇒ did not start; signed out or sign-in closed ⇒ it did, quarantine, host recovery); the only button is "Reload this page" |

No terminal page has a retry control (asserted). The runbook link is rendered only when the container supplies `runbookHref`;
the page never invents a URL (the runbook is written in P1.18.3).

### 4.3 Reapproval (`ReviewScreen`, route `/restore/review`)

`{ load: ManifestLoad, approval: ApprovalState, inspectHref?, credentialsHref, onRetry, onApprove(items), initial? }`.

* **Page-level `load`**: `loading` (Skeleton), `failed` (never an empty list), `denied`, `no_restore` (the 404; an explanation, not an
  error), `ready`.
* **Summary** of the latest restore (backup id and type, restored at, origin, counts waiting/approved, credentials kept inactive).
* **Waiting for approval**, grouped Endpoint / Users / Groups / Agents / Group members / Rules. A record has a checkbox **only if**
  the service sent `approvable: true`; the rest sit under *Not approved here* with their fixed reason in words:
  `single_administrator` ("one administrator, and the host recovery sets who it is"), `needs_reverification` ("verified again by the
  person it belongs to"), `unsupported`.
* **Selection bar**: a polite count, *Clear selection*, and **Approve N selected…** (disabled at 0 and above 500). It opens a
  `ConfirmPanel` (warning tone) that lists every named record, says all-or-nothing and that no credential comes back.
  `onApprove` receives **only `{kind, id}`** in manifest order (the service orders dependencies itself).
* **Imported against applied**, side by side, for exactly two comparisons (`Comparison`):
  `mfa` (user: imported vs effective second-factor requirement, plus the file's `compromised` flag) and `rule` (policy: imported vs
  effective Allow/Deny, `localDenyKept`). A difference is warn-toned and written out ("Approving applies the setting on the right, not
  the one in the file", or "A Deny rule with this id already existed here and was kept"). The page never says which setting is stricter.
* **Per-record notes**: *Not in the file* (kept from this installation, switched off, never deleted); `source_state` only when it is not
  `active`, labelled reference-only; credential follow-up (a pending user/agent: approving restores no sign-in method/token; an approved
  agent: link to the P1.16 Agent tokens page via `credentialsHref`); *See details* link via `inspectHref` (P1.17 pages show a restored
  record as "Waiting for approval" with its full sentence, so the manifest's thin rule label is not the only place to read a rule).
* **`approval`**: `working` (confirm busy); `done` (success, focus, selection cleared); `conflict` (danger, focus: *Nothing was approved*, each
  refused record by name with its fixed reason, rows flagged, **selection kept**); `rejected` (`denied` / `invalid` / `rate_limited` /
  `still_quarantined` / `outcome_unknown`). `outcome_unknown` says some or all records **may** have been approved and offers *Reload the
  list*, never a repeat.

## 5. Focus and keyboard

| Moment | Behaviour |
| --- | --- |
| Outcome appears (export result, restore refusal, acknowledgement request, approval result, any terminal page) | focus moves to that alert (`useFocusWhen`, tabIndex -1), so a screen-reader or keyboard user lands on the answer, not on a control that just vanished |
| Confirmation opens | focus on its group (name = the question and the file); Tab → *(acknowledgement)* → phrase → confirm → Cancel |
| Escape / Cancel | closes it and returns focus to the button that opened it (a **bug found and fixed here**: the first version unmounted that button, so focus fell to `<body>`; a test now pins it) |
| Wrong phrase / unticked acknowledgement | inline error, focus returns to the offending field, **no request** |
| Enter in the phrase field | confirms, exactly like the button |
| Busy | the confirm button keeps focus (`aria-busy`, not `disabled`), repeats are ignored, Escape and Cancel are ignored |
| After a closed answer | the confirmation closes so the answer is what is read; reopening means typing the phrase again (acknowledgement: the phrase is kept) |

Tab order was walked with real key events in a browser on S-d, V-b and X-b (every stop shows a focus indicator).

## 6. HTTP outcome → state (the mapping the containers implement)

`src/screens/recovery/outcomes.ts` is this table as code, with tests. Callers first handle a 401 ("your session ended" in the signed-in
frame) and a 403 `step_up_required` / `assurance_unavailable` (open the P1.16 StepUpGate in place; **the blocked request is not replayed**; the
form stays as it was; the person presses the button again).

| Route | Response | State |
| --- | --- | --- |
| export | 200 attachment | `done` (`X-Backup-Id`, `X-Backup-Mode`, filename from `Content-Disposition`) |
| export | 403 / 400,415 / 429 / anything else | `rejected`: `denied` / `invalid_request` / `rate_limited` / `unavailable` |
| restore | 200 `{report, authorizer_notified, session_ended}` | **`RestoreEnded.complete`** (replace the shell; do **not** mount `SignedIn`, whose 401 handling would navigate away) |
| restore | **any** failure with `installation_state: "restore_quarantine"`, or code `restore_superseded` | `RestoreEnded.incomplete` (`superseded` for that code) |
| restore | status 0 (network, **timeout**), a 2xx whose body did not decode, 500/502/504, a 503 that is not the documented `unavailable` | `RestoreEnded.unconfirmed` |
| restore | 409 `provenance_unverified` | `needs_acknowledgement` |
| restore | 422 `archive_malformed` / `_unsupported_version` / `_integrity_failed` / `_inconsistent` (unknown 422 → malformed) | `rejected` with that reason |
| restore | 403 / 429 / 503 `unavailable` (no installation_state) / other 4xx | `rejected`: `denied` / `rate_limited` / `unavailable` / `invalid_request` |
| manifest | 200 / 404 `no_restore` / 403 / other | `ready` / `no_restore` / `denied` / `failed` (401 while quarantined → sign in) |
| approvals | 200 `{approved: […]}` | `done` (count) then reload the manifest |
| approvals | 409 `conflict` + `items` | `conflict` (unknown kinds dropped, unknown reasons → `other`) |
| approvals | 409 `restore_quarantine` / 403 / 429 / 400 | `still_quarantined` / `denied` / `rate_limited` / `invalid` |
| approvals | status 0, a non-decoding 2xx, **any 5xx including 503** | `outcome_unknown` (an approval can commit and then fail to notify, as in P1.17) |

## 7. Component and API boundaries for P1.18.3

**What this contribution does not do** (all of it is P1.18.3's, or later): no fetch, no CSRF, no step-up, no `web/assets.go` route
allowlist, no `navFor` change, no container, no archive handling, no download, no authorization decision, no automatic reactivation.

**What the container must do:**

1. **Transport (`src/api/http.ts`).** `ApiResult` keeps only `status`, `code` and `guidance`. It must also carry, strictly validated
   (string `installation_state`; array of `{kind, id, reason}` capped at 500), the two documented fields `installation_state` and `items`,
   or `restoreOutcomeOf` / `approvalOutcomeOf` will misread every post-transition failure as "nothing changed".
2. **Timeouts.** `send()` aborts at 20 s. A restore of a large archive (the service allows 16 MiB and a two-transaction import) and an export
   can exceed that. A client abort of a restore is **not** a failure, it is `unconfirmed`: raise the bound for these two calls (the screens
   already show a long-running state).
3. **Request bodies.** Export `{mode}`. Restore `{archive, confirm: RESTORE_PHRASE, acknowledge_unauthenticated_provenance}` — the screen
   hands over the `File`; the container reads it, and decides how to embed it (the service HMACs decoded fields, so re-serialising is safe).
   Approvals `{items: [{kind, id}]}` exactly as `onApprove` delivers them.
4. **Download.** Export success: turn the response body into a download with the `Content-Disposition` filename, revoke any object URL, retain
   nothing, then set `done`. The screen never sees the bytes.
5. **Step-up.** Classes `backup-export`, `backup-restore`, `security-policy-change` use the existing `useStepUp` / `StepUpGate`. The action
   labels to pass: "Export a backup", "Restore a backup", "Approve restored records".
6. **Shell and routes.** Add `RECOVERY_NAV` to `navFor` for administrators only, `RECOVERY_ROUTES` to `web/assets.go`'s exact allowlist (and its
   test), the three views to `App.tsx`, and `'backup-export' | 'backup-restore' | 'backup-review'` to `PageId`. `/recovery` is already the
   P1.16 sign-in; these routes deliberately avoid it. The Recovery nav group gets its own heading.
7. **After a closed restore.** Render `RestoreEndedPage` in place of the shell. Do not re-read the session, do not poll, do not auto-retry.
   `onReload` is the container's reload.
8. **Review page wiring.** `inspectHref(kind, id)`: user → `/policy/users`, group and memberships → `/policy/groups`, agent →
   `/policy/agents`, policy → `/policy`, endpoint/role/address → `undefined`. `credentialsHref` → `/agents` (`AGENT_TOKENS_ROUTE`). Reload the
   manifest after every `done` and after `outcome_unknown`.
9. **Decoding the manifest.** Map `imported`/`effective` onto `Comparison` only for `user` (`mfa_requirement`: `optional|required|webauthn`,
   `compromised`) and `policy` (`effect` lower-cased; `localDenyKept` ⇔ `effective.note` present or imported Allow with effective Deny). For every
   other kind, and for every `approved` item, use `{kind: 'none'}`. Fail closed on any other shape (the page then says it could not load).
   `restored_at` is Unix seconds; `summary.credentials_stripped` feeds `credentialsStripped`.

## 8. Not designed here, deliberately

* **A sign-in page for a quarantined installation.** The P1.18.1 contract defines no signal the login page could read. After a restore, sign-in
  simply fails; the terminal page and the runbook are where the explanation lives. A message on `/login` needs a server field first.
* **A preview of the archive's contents or its provenance.** The service has none (docs/backup-restore.md §7). The acknowledgement flow (§3)
  is the workaround that needs no new API.
* **The host recovery ceremony** and its runbook (P1.18.3 and a later card). The pages say it exists and that a browser cannot do it.
* **How a non-administrator user's sign-in method is set up again.** `needs: credential_enrollment` is shown as "no sign-in method yet; none is
  restored". The flow that enrols one is outside P1.18.1.
* **Rule detail in the manifest.** The service label is `Effect + operation` only. The page links to P1.17 for the full sentence instead of
  inventing a subject or selector.

## 9. Assumptions to validate (coder / reviewer)

1. The refusal codes `owner_not_active` and `not_quarantined` exist in `internal/backup/approve.go` but are absent from the table in
   `docs/backup-restore.md` §5; the page handles both and maps any unknown code to "Mandatary refused it".
2. `restore_superseded` is always raised after the first transaction. If the service ever sends it without `installation_state`, the page still
   shows quarantine (conservative: it tells the person to run the host recovery, which is harmless if unnecessary).
3. A `compromised` flag in the file is shown loudly but does not hide the checkbox (`approvable` is the server's field); the service refuses it with
   `compromised`, and the conflict list says so. If the product prefers to hide it, that is a service change (`approvable: false`).
4. "Still signed in ⇒ the restore did not start" (the `unconfirmed` page) relies on the first transaction revoking every session. P1.18.1 does so;
   re-verify if that changes.
5. The 15-minute freshness window is deliberately absent from the copy: the pages say "recent", because the window is the service's.
