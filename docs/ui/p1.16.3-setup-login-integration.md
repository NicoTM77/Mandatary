## 2. HTTP contract implemented

No existing contract was changed. All routes are behind `auth.Browser` (exact Host/Origin, JSON only, 64 KiB
body bound, server-derived CSRF on unsafe methods, strict headers) with an explicit `RoutePolicy`.

| Route | Policy | Request | Outcomes |
| --- | --- | --- | --- |
| `POST /api/v1/login` | `RequireNone` | `{username, password}` | 200 `{step:"factor", next:[…], csrf_token}` + preauth cookie · 200 `{step:"session"}` + session cookie (optional-MFA account with no second factor and a ≥15-code-point password) · 401 `unauthenticated` (**one** outcome: unknown user, wrong password, exhausted factor, account wait) · 400 · 503 |
| `POST /api/v1/login/totp` | `RequirePreauth` | `{code}` | 200 `{step:"session"}` (cookie rotated; AAL2) · 403 `denied` (wrong, replayed, throttled, exhausted and "several factors" are one outcome) · 401 (capability ended, cookie cleared) · 403 `forbidden` (Origin/CSRF) |
| `POST /api/v1/login/no-mfa` | `RequirePreauth` | `{}` | 200 `{step:"session"}` (lower assurance) · 403 `denied` (policy refuses; mandatory MFA) · 401 |
| `GET /api/v1/session` | `RequireSession` | – | 200 the `SessionInfoHandler` labels **plus `username`** (non-secret) · 401 |
| `POST /api/v1/logout` | `RequireSession` | `{}` | 204 + cookie cleared · 401 · 503 (session kept) |

Every route also refuses any query string (404). The server picks the TOTP authenticator itself: the page has
no authenticator identifier, and an account with more than one live TOTP factor is refused (not guessed)
until slice 2 adds a selection step. WebAuthn login, step-up and recovery are **not** routed
(`cmd/mandatary/account_startup_test.go` and the browser matrix assert this).

CSRF token handling: the token returned by the preauth/session responses lives only in a private field of
`AccountApi` / `SetupApi` (memory). It is sent as `X-CSRF-Token`, never a cookie, query or body, and is never
rendered. Passwords, setup tokens, TOTP codes and the TOTP seed are arguments of one call (or, for the seed,
the single state that displays it) and are dropped afterwards.

## 3. §10.3 assumptions, validated against the real code

| # | Assumption | Result | Evidence |
| --- | --- | --- | --- |
| 1 | `exchange` returns the same 401 `invalid_token` for wrong, expired and replayed tokens | **Holds** (`setup_http.go`: every `ErrSetupDenied` is 401 `invalid_token`). Nuance: once an expired generation has been cleaned up (30 s tick) the whole surface is 404, so an expired token is `closed`, not `invalid_token`. Both disclose nothing else; the UI has copy for each. | browser `setup-replay-expiry` (replayed vs garbage token: identical text; expired → token form before cleanup, `Setup isn't open` after) |
| 2 | `403 denied` on address/TOTP confirm cannot be told from a wrong code | **Holds.** Throttling is a separate 429 `rate_limited` (connection-scoped, not account-scoped), which the UI shows as such. | `containers.test.tsx` |
| 3 | TOTP begin algorithm; seed only once; restart | The server accepts exactly `"SHA1"` or `"SHA256"` (not `"SHA-256"`); the UI sends `SHA256`. | 4 | Login keeps generic 401 parity | **Holds.** `PasswordLogin` maps every failure to `ErrDenied`; bodies are byte-identical. `recovery_required` is not offered (no account-independent signal exists). | `TestLoginHTTPPasswordThenTOTPEndToEnd`, browser |

## 4. Defects found in the baseline and decisions

* **`mfa_reset` account step.** `StageAccount` refuses a non-empty username or any address for that purpose.
  The presentational form hands back `username = targetUser`; the container therefore sends **only the
  password** (asserted at the API layer, the container layer and with a mutant).
* **Static handler answered POST with 405 before routing**, so an unmounted API path is 404 for GET and 405
  for POST. Tests accept either for "not routed" and require that no service ran and no cookie was set.
* **Contract addition** (`contract.ts`, `login.tsx`): `LoginFactorState` gains `password_only_refused`, so a
  server refusal of the password-only step (mandatory MFA) is not mis-shown as "That code wasn't accepted".
* **Heading outline.** Pre-session frames had no `<h1>`; the containers add a screen-reader-only `h1`
  (`First-time setup`, `Sign in to Mandatary`).
* **Proof send refused (403)** is shown as the wait-and-retry state (`rate_limited`): the server cannot say
  more, and "wrong code" would be false.
* **Primitives from P1.16.2:** `deriveSetupClock`, `Skeleton` and `formatDate` are adopted. `EmptyState` is
  not (slice 1 has no empty list). `formatMinutes` is not (the pluralisation lives in `SetupClockNotice`, which
  P1.16.2 could not edit).
* **Seed lifetime.** The TOTP seed is held only in the `seed_shown/confirming/rejected` states. It is dropped
  when the code is proven, when the setup session ends (401), and when the deadline timer fires. A reload
  after begin shows `seed_lost`.
* **Preauth timeout** is also shown locally after five minutes; the server remains the authority.

## 5. Tests

RED→GREEN: the Go adapter tests, the allowlist/CSP tests and the browser tests were written first and failed
first (compile error `undefined: RegisterAccountRoutes`; `TestApplicationDocumentRoutesAreAnExactAllowlist`
and the CSP test failing on `/setup`, `/login` and `connect-src`; the browser run against the unchanged
skeleton bundle timing out on the setup heading). The frontend API/container tests were written after the
containers and were verified with mutants instead (each listed mutant fails its targeted test).

Browser scenarios (each runs against a fresh real installation, in `light` and `dark` colour schemes, against
the production bundle):

* **setup-login:** token exchange → account → address proof through the real mail path → TOTP key shown once →
  wrong then right code → finish → first ordinary login (no password-only offer for an administrator) →
  signed-in home labelled multi-factor → reload/back/forward → theme toggle → sign out; cookie attributes
  (`__Host-`, HttpOnly, Secure, SameSite=Strict, session-only), password-manager attributes, paste not blocked,
  no secret on any DOM/URL/title/storage/console/network/log surface, no setup session issued by completion.
* **setup-replay-expiry:** a replayed token is indistinguishable from a garbage token; the 30-minute deadline
  passing mid-flow ends the flow; the surface closes after cleanup.
* **login-flows:** unknown user = wrong password; wrong code; idle expiry while the page is open; labelled
  lower-assurance path; five-minute preauth expiry; 19-case direct-request matrix (no CSRF, wrong CSRF,
  foreign/missing Origin, cross-site fetch metadata, form post, duplicate headers, unknown fields, assurance
  asserted by the client, query-string credentials, forged/duplicate/setup cookies, foreign Host,
  unrouted slice-2 routes); mandatory-MFA policy (no password-only step; direct call refused 403).

## 6. Outstanding, limits and honest gaps

* **Slice 2 is outstanding** (P1.16.4): factor lifecycle, recovery, step-up, addresses (F7 has no backend),
  notice health, agent-token reveal-once, WebAuthn login/enrolment and a selector for several TOTP factors.
* **Login exists only when the server has a notice relay.** `auth.Lifecycle` (and therefore `Sessions`) is
  built only from the notice settings; without them the login routes are not mounted. An installation that
  has finished setup but loses its relay configuration therefore cannot sign in. This follows from the
  existing architecture and was not changed here.
* **Chromium only** (Playwright's, headless). Firefox, WebKit/Safari, branded Chrome/Edge, real password
  managers, real autofill, screen readers and real authenticators are **unverified**. No automated
  accessibility scanner was run (none is installed); the structural checks are in the unit tests.
* The test clock for the `login` fixture sits in 2033 (the pre-seeded session fixture), so the displayed
  session deadline in those runs is not a real date. The setup fixture uses the real clock.
* The page cannot observe idle expiry without making a request (a poll would itself count as activity); it
  learns of it from the next request's 401 and shows "Your session ended" or goes to sign-in.
* TOTP SHA-256 authenticator-app compatibility (§3 row 3) needs an owner decision and real-app evidence.
* The container tests use a fake server for outcome mapping; they are not evidence of service behaviour.
  The real services are exercised only by the Go adapter tests and the browser tests.
