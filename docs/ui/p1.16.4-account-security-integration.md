# P1.16.4 account-security integration (slice 2)

Contribution P1.16.4 (`t_3ab2f0ae`) to P1.16 (`t_233b6816`), on top of
[P1.16.3](p1.16.3-setup-login-integration.md). Local contribution on the P1.16 branch: not a PR, not
independently reviewed, and **not** a NIST, FIPS, accessibility-conformance, browser-support or product
claim. The P1.16 acceptance gate (consolidated integration, publication and independent review) remains
outstanding. The presentational baseline is [p1.16-authentication-ux-contract.md](p1.16-authentication-ux-contract.md).

The adapters add **no authority**. Every proof and every state change goes through an existing service
(`Sessions`, `Lifecycle`, `WebAuthnService`, `Admin`); the one new service function, the post-setup address
service, only applies the rules the setup address path already enforces.

## 2. HTTP contract implemented

All routes are behind `auth.Browser` (exact Host/Origin, JSON only, bounded body, server-derived CSRF on
unsafe methods, strict headers) with an explicit `RoutePolicy`; none accepts a query string (404). The TD §4.3
mutation classes are registered on the route, so the freshness/assurance gate runs before the handler and
again inside the service transaction. No request field can set an assurance, method, role, time or
authenticator class (unknown fields are a 400).

| Route | Policy / class | Request → outcome |
| --- | --- | --- |
| `GET /api/v1/account/security` | session | inventory (apps, keys, saved-code **count**, addresses, notice-health **counts**) · 403 `denied` for a session without authority to see it (password-only on an MFA-capable account) · 401 · 503 |
| `POST /api/v1/stepup/password` · `/stepup/totp` | session | `{password}` / `{password, code, authenticator_id?}` → 200, **successor session** (new cookie and CSRF token, predecessor revoked) · 403 `denied` (a password cannot step up an MFA-capable account; replay, wrong, ambiguous) |
| `POST /api/v1/stepup/webauthn/begin` · `/finish` | session | server-issued ceremony; finish verifies origin, RP ID, challenge, user verification and owning session · 200 successor |
| `POST /api/v1/account/totp` · `/confirm` | authenticator-change | 200 `{authenticator_id, secret, …}` (**reveal-once**) · 204 |
| `POST /api/v1/account/totp/remove` · `/webauthn/remove` | authenticator-change | 200 `{signed_out:true}`; **every session of the account ended**, cookie cleared · 403 (last required factor) |
| `POST /api/v1/account/webauthn/register/begin` · `/finish` | authenticator-change | ceremony; finish binds the credential · 204 |
| `POST /api/v1/account/recovery-codes` | authenticator-change | 200 `{codes[10]}` (**reveal-once**; replaces the previous batch) |
| `POST /api/v1/account/addresses` · `/proof` · `/confirm` · `/remove` | notification-address | 201 `{address}` (staged, unused) · 204 (mails a one-use, expiring proof to the **proposed** address only) · 204 · 204. At least one confirmed address always remains; the other addresses are told of a proposal and of every change. A logical refusal (unknown or foreign address, wrong or used proof, last confirmed address, limit) is the one opaque 403 `denied`; a storage fault (transaction, read, write, commit, randomness) is a fixed 503 `unavailable` with no SQL text, no success claim and nothing committed (P1.18.4 P116-L5, `TestAddressHTTPStorageFaultsAreUnavailableNeverDeniedAndChangeNothing`) |
| `POST /api/v1/login/webauthn/begin` · `/finish` | preauth | key sign-in; user verification required by the server · 200 `{step:"session"}` |
| `POST /api/v1/recovery` | none | `{username, password, code}` → 200 `{step:"capability", csrf_token, expires_at, methods, replacement_code}` + `__Host-mandatary_recovery` cookie · 403 (one outcome for unknown user, wrong password, wrong/used code, throttle) |
| `GET /api/v1/recovery/state` · `POST /recovery/totp` · `/totp/confirm` · `/webauthn/begin` · `/finish` | capability (CSRF derived from the capability secret) | re-enrolment; completion issues **no session** · 401 once the ten minutes pass |
| `/api/v1/admin/agents[/{id}/credentials[/rotate\|/{credential}/revoke]]` | P1.10 policies | issue/rotate return the token **once**; revoke is immediate |

The recovery capability and the session are distinct credentials: neither opens the other's routes
(browser `denial-matrix`).

## 3. The SPA

* **`SignedIn`** is the shared frame: loads `GET /session`, shows the server's own labels, handles 401 (go to
  sign-in), idle/absolute display, and a sign-out that is never presented as done unless the server confirmed.
* **Step-up gate (`StepUpGate`)**: a 403 `step_up_required` opens the in-place panel offering only the proofs
  the **server** listed in `step_up_methods` (never computed by the page); a 403 `assurance_unavailable` shows
  the no-retry state. On success the page adopts the successor session (new CSRF token), says so, and **does
  not replay the blocked request**: the person repeats it. Pending ceremonies and revealed secrets are dropped
  when the panel opens.
* **Reveal-once**: the TOTP seed, the ten saved codes, the replacement saved code and the agent token each
  live only in the one state that shows them and are dropped when hidden, when a step-up replaces the session,
  when the capability ends, and on reload (a reload cannot restore them; they are never in the URL, storage,
  title, console, history or a list response).
* **Removal ends every session**: the page shows "Sign-in method removed" and offers sign-in; it keeps nothing.
* **Notice health** shows aggregate counts of **the signed-in account's own notices only**, computed by the server (`AccountNoticeHealth`, one user-scoped query). Installation-wide counts and other accounts' recipients, events or counts are never in this payload; no ordinary user has a global-scope option (P1.18.4 P116-L3, `TestSecurityInventoryNoticeCountsAreScopedToTheSignedInAccount`). It shows "unknown" when the status is unreadable (never healthy).
* **Several authenticator apps**: the person names which app the code is from; the page sends that
  authenticator identifier. One app sends none. The server never guesses.
* **Security keys**: the server issues the ceremony; the page hands the options to the browser and the browser's
  credential back **unmodified**. The page keeps no key name (the service stores none).

## 4. Decisions and findings

* **Notification addresses** had only the setup path. A post-setup service (`address_service.go`) was added; it
  requires fresh max-strength evidence, uses one-use expiring proofs, keeps at least one confirmed address and
  caps addresses at the setup limit. The proof mail text no longer says "setup form".
* **WebAuthn from one origin.** The relying-party ID is the host of the trusted public origin and the only
  allowed origin is that origin; Host and forwarded headers are never consulted. If the pair is not acceptable
  to the WebAuthn service (an IP literal, a public suffix) **no key route exists** and the page says keys are
  unavailable.
* **Inventory for a password-only session** is refused with 403 (the lifecycle read floor), not shown, and the
  page explains it and offers verification. (Found by the browser test; a RED/GREEN Go test was added.)
* **`credentials: null`** for an agent with no credential is accepted as an empty list.
* **ES256 only.** The WebAuthn service offers only ES256 (existing, approved key policy). Chromium prints a
  console advisory about it when a key is registered; the key scenario allows that one message and nothing
  else.
* **Own-session management and general notification features are not added** (later phases). No new
  dependency.

## 7. Outstanding, limits and honest gaps

* **Chromium only** (Playwright's headless build). Firefox, WebKit/Safari, branded Chrome/Edge, real password
  managers, real screen readers and real authenticators are **unverified**. The WebAuthn tests use Chromium's
  virtual authenticator (CTAP2, UV on).
* **No axe-core (or other scanner engine) is installed**: adding one is a new dependency that needs separate
  approval. Instead `web/tests/a11y-audit.mjs` is a dependency-free structural audit run by `scanSurfaces`, so
  at **every scanned page state of every browser scenario, in both themes**, it checks: document language and
  title, one `main`, one level-1 heading, heading order, duplicate ids, `aria-*` references, accessible names
  of every control, form-control labels, image alt, `aria-hidden` focusables, positive tabindex, WCAG 1.4.3
  colour contrast on resolved colours (4.5:1 / 3:1 large), and a real-keyboard Tab walk (every enabled control
  reachable, every stop with a visible focus indicator). The scenario `a11y-selfcheck` proves the audit
  detects each rule on deliberately bad markup and passes good markup. It found one real pattern on first use
  (the step-up password-manager username hint is `aria-hidden` and untabbable: exempted by rule, documented in
  the audit) and one test race (auditing mid-reload; the audit now waits for `aria-busy` to clear).
  This is a **bounded structural check, not axe, not a WCAG conformance claim**, and screen-reader output,
  reading-order semantics, zoom/reflow, reduced-motion and touch-target sizes are **not** evidenced. The
  "supported-engine accessibility matrix" of the original card is only evidenced on Chromium (see above).
* **TOTP algorithm**: the page asks for SHA-256 (the service default). Authenticator apps that only support
  SHA-1 may reject it; there is still no `otpauth://` URI or QR code (unchanged from slice 1).
* **Key names**: not collected (no schema field). Keys are listed "Security key N".
* **Fixture clock**: the security fixture's server clock starts at the real present, but the test advances it
  (sixteen minutes to hours) while the browser keeps its real clock, so countdown text in these runs is not
  meaningful.
* **Mail**: the receiver is a loopback TLS SMTP server; no real mail leaves the machine.
