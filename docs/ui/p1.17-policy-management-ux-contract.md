# P1.17 policy-management UX contract and presentational baseline (P1.17.1)

Contribution P1.17.1 (`t_bb9cfd69`) to P1.17 (`t_96a82771`). This page is the design and state
contract that the P1.17.2 containers (HTTP, step-up, routing) build against. It is a **design
contract and a presentational baseline, not working administration**. Nothing here is a NIST, FIPS,
accessibility-conformance, browser-support or product claim. Every state labelled *synthetic* is an
illustration, and every assumption in §9 must be validated by the coder against the real services.

Source of truth for behaviour stays in `docs/authorization.md`, `docs/agent-credentials.md`,
`docs/storage-schema.md`, `technical-decisions.md` and the P1.16 contract
([p1.16-authentication-ux-contract.md](p1.16-authentication-ux-contract.md)). This page only decides
how those contracts are presented. Where a screen needs something the backend does not yet expose,
§8 lists it as a proposal for the coder, never as an existing API.

## 2. The authority model the screens enforce in words (and never in code)

1. **Nothing in the UI is authority.** Hiding a link or disabling a button is presentation. The
   server validates and enforces every request; a screen that is shown to the wrong person exposes
   nothing, and a hidden screen protects nothing. `Load.denied` renders the same refusal for "not the
   administrator", "no second factor" and "authority changed", because the server does not
   distinguish them to the caller and neither may the page.
2. **Administrative authority is not container permission.** Every management page carries the same
   always-visible note (`AuthorityNote`, not collapsible): *the policy administrator decides who may do
   what, but the role allows no container operation by itself. Owning an agent allows none either. Only
   a rule that names an account, a group or an agent does.* The administrator is badged "Policy
   administrator" wherever shown and is offered in the rule editor like anyone else, with a note that
   the role grants nothing.
3. **A rule is the only grant.** No screen offers "owner can do X", no owner shortcut, and ownership
   is labelled "accountability only". Membership is labelled as the thing that makes a group's rules
   reach someone, and "owning an agent doesn't make it a member".
4. **Default is refusal.** The empty state says every request is refused, including the
   administrator's own. Mandatary and its peer containers are never listed and can't be targeted.
5. **No evaluator.** `selector.ts` mirrors the server's *documented* limits to give early feedback
   (name charset, hex lengths, ceilings). The server remains the authority and may refuse what the page
   accepted; §6 maps that to presentation.
6. **Secrets stay out.** Nothing here handles a token, password or code. Tokens are issued, rotated and
   revealed once on the P1.16 Agent tokens page; the Agents screen only links there
   (`credentialsHref`). `source.test.ts` asserts the contract has no secret-shaped field.

## 3. Design language

Reuses P1.16's shell, tokens and motion unchanged (`AdminShell`, `Panel`, `Alert`, `Badge`, `Button`,
`Field`, semantic Tailwind tokens from `style.css`). Both themes come from tokens: `source.test.ts`
fails on any `dark:` variant, raw colour or inline style in the new sources.

Decisions specific to this work:

* **State is never colour alone.** Allow and Deny differ by word *and* icon; every badge pairs an
  icon with text ("Disabled", "Waiting for approval", "Inactive · target missing").
* **A rule reads as a sentence**, built once (`ruleSentence`) and used as the row heading, the
  accessible name of every row button ("Delete: Allow agent sample-ci-runner to read logs of
  sample-edge-proxy") and the confirmation title. A reviewer reading the page reads what the system
  will do.
* **Risk is shown where it is created.** Selector strength is classified into five levels (`pinned`,
  `guarded`, `name_only`, `pattern`, `broad`) and shown in the editor as it is typed and as a "reach"
  badge on rows. A *broad Allow* (matches every container, or a pattern with no identity check and a
  state-changing operation) cannot be saved until the person ticks that they mean it. A broad *Deny*
  needs no tick: blocking more is not a risk to confirm.
* **Loosening vs tightening is told apart.** Deleting or disabling a Deny, or enabling an Allow,
  *loosens* access: its confirmation is `warning` toned and says what becomes possible. Disabling or
  deleting an Allow *ends* access: `danger` toned, and says that open streams are cut.
* **Native controls only** (`Choice.tsx`): `<select>`, radios, checkboxes. No custom widget, so
  keyboard, screen-reader and autofill behaviour are the browser's. Secrets still use the uncontrolled
  `TextField` family; choice controls are for non-secret values only.
* **One confirmation pattern** (`ConfirmPanel`, D-CONFIRM-1, lifted from P1.16): inline, named,
  `role=group`, Escape cancels and returns focus to the control that opened it, the confirm button
  announces progress (`aria-busy`, stays focusable) and ignores repeat presses.
* **Disclosure** (`Disclosure.tsx`) is a native `<details>` with a visible chevron. The `open` prop only
  ever *opens* it, so a panel never closes under a person who is typing in it.

it only for a session whose view says it is the administrator (as P1.16's `navFor` does for Agents).
Routes are exact paths (D-ROUTE-1; no wildcard fallback), **owned by P1.17.2** which must add each to
the allowlist in `web/assets.go`:

| Path | Screen |
| --- | --- |
| `/policy` | Rules |
| `/policy/users` | Users |
| `/policy/groups` | Groups |
| `/policy/agents` | Agents (identity and ownership) |

**Naming collision to resolve at integration:** P1.16's existing nav item is labelled "Agents" and leads

## 5. Screen and state map

Every screen is a stateless function of `(load, mutation, pending, data, callbacks)`. They never call
`fetch`, touch storage, interpret a status code or decide permissions.

### 5.1 Page-level states (all four pages)

| `load` | Presentation |
| --- | --- |
| `loading` | `Skeleton` with a polite status "Loading …"; no form, no button, no list. |
| `failed` | `Alert` "Couldn't load …" with **Try again**; **never an empty list** ("Nothing was changed"). |
| `denied` | `Alert` "Policy administration isn't available to this session", says nothing about who is; no form, list or button. |
| `ready` | The page. |

### 5.2 Outcome of the last command (`mutation`)

`target` is a row id, `create` (the create form) or `editor` (the rule editor); an outcome renders only
where its target is, and focus moves to it when it appears.

| `Mutation` | Presentation |
| --- | --- |
| `idle` | nothing |
| `working` | the button that started it shows progress (`aria-busy`, label "Saving…", stays focusable, ignores repeats); siblings that would conflict are disabled |
| `done` | success `Alert` with the container's sentence ("Added sample-fresh. They have no access yet."); create forms clear |
| `rejected: denied` | "That change wasn't allowed" |
| `rejected: not_found` | "That no longer exists… Reload the list" |
| `rejected: conflict` | "That conflicts with what exists" (name used, account disabled, still referenced) |
| `rejected: invalid` | "That wasn't accepted" |
| `rejected: rate_limited` | shared P1.16 copy |
| `rejected: outcome_unknown` | **"Mandatary couldn't confirm the result"**; says it *may or may not* have been saved, offers **Reload the list**. Never says "nothing was changed". |

`outcome_unknown` exists because the service reports a failed policy *notification* after a durable
commit as the same 503 as a failed write (§9, item 3).

`step_up_required` is **not** a reason. The container opens the P1.16 `StepUpGate` in place and keeps
the form as it was; the blocked request is not replayed, so the person presses the button again.

### 5.3 Users (`UsersScreen`)

List of rows: name, state badge, "Policy administrator" badge, groups, owned agents, rule count, rule
link ("View rules for sample-sam"). Actions per row: **Disable** (active) / **Enable** (disabled),
**Delete**. Rules:

* The administrator has **no** lifecycle buttons and says "has no container operations unless a rule
  names it". A restored (`quarantined`) account has none either: it is "Waiting for approval" and can
  only be approved through the restore flow (P1.18).
* **Delete is disabled with its reasons written beside it** when the server says it is not allowed:
  "Can't be deleted yet: owns agent sample-ci-runner; has 2 rules; belongs to sample-ops."
  (`Removal.blockers`, decided by the server; the page never computes it.)
* Only actions listed in `actions` are rendered at all (D-NAV-1: no control for something that does not
  exist). Anything listed must work end to end.
* **Create** is one field, `Username`, validated against `IDENTIFIER_RULE` (the server's rule). No
  password is collected: sign-in credentials are P1.16's concern.
* Confirmations: Disable ("can't sign in… rules and memberships are kept but grant nothing until
  enabled"), Enable, Delete ("permanently removes… can't be undone").

### 5.4 Groups (`GroupsScreen`)

Members are shown per group, mixed users and agents, each with its own state and the **membership's**
state. A restored membership is "Membership waiting for approval… grants nothing until it is approved
explicitly". An empty group says "rules for this group apply to nobody".

* **Add member**: one grouped `<select>` (Users / Agents) of people not already in the group. A
  disabled account stays *visible but unavailable* ("sample-robin (disabled)") so the list explains
  itself. Nothing chosen is refused inline.
* **Remove member** is confirmed and warns: "that includes any Deny rules, so X may gain access that
  another rule allows".
* **Disable group** warns that Deny rules in it may stop applying. **Delete** is blocked while it has
  members, owns an agent or has a rule, and says which.

### 5.5 Agents (`AgentsScreen`, identity only)

Name, state, **owner** ("Accountability only. Owning an agent gives neither the owner nor the agent any
access."), groups, live-token count, rule count, link **Manage tokens for X** (`credentialsHref`).

* The owner is **a user XOR a group**: the create form is a two-way radio plus the one matching
  `<select>`; the payload carries exactly one `OwnerRef`. Only *active* accounts are offered. If no
  user is active the group choice is preselected so the form is never stuck on an empty choice.
* **Change owner** is an inline form that excludes the current owner and says "only who is accountable
  changes: the agent keeps exactly the access it has now". Escape cancels and returns focus.
* **Disable agent** says "Every token is revoked for good, and any stream it has open is cut off. Rules
  that name it are kept but grant nothing."
* No issue/rotate/reveal/copy control exists on this page, and a test asserts it.

### 5.6 Rules (`RulesScreen`) and rule editor (`RuleEditor`)

**Page.** Endpoint named ("Local (Docker socket on this host)"); a "How Mandatary decides a request"
disclosure (Mandatary itself refused → credential valid → any Deny wins → an active Allow must match →
otherwise refused; the administrator role and ownership are explicitly *not* in the list). Filters:
decision, subject kind, "Needs attention only", with a live "Showing 3 of 9".

**Missing-target visibility.** A rule whose selector matches nothing stays on the page, flagged
**"Inactive · target missing"**, with what that means: for an Allow "this grants nothing and requests for
it are refused… Mandatary keeps the rule rather than deleting it"; for a Deny "this blocks nothing yet,
but will if a match appears". A summary line counts them and offers **Show rules that need attention**.
If the backend cannot prove its own identity (`endpoint.safety = unverified`, SELF-01) a page-level alert
says every operation is refused whatever the rules say, and rows show **"Target status unknown"**, which
is **never presented as a match**.

**Row.** One sentence heading, Allow/Deny badge, state badge, the selector's identity checks as chips
("Compose project sample-shop", "Container ID a1a1a1a1a1a1…") or "No identity checks: the name alone
decides.", limits ("at most 500 log lines per request"), the reach badge, and Edit / Enable / Disable /
Delete. A restored rule (`quarantined`) can only be deleted here.

**Editor** (create and edit share one form; the draft is local and sent **once**, at submit):

1. *Applies to*: radio User / Group / Agent, then a `<select>` of that kind. Disabled accounts visible
   but unavailable. Choosing the administrator shows "This is the policy administrator… allows no
   container operation. This rule would be the only thing that gives this account any."
2. *Decision*: Allow / Deny radios.
3. *Operations*: **exactly the six approved** (`container:logs`, `inspect_status`, `inspect_config`,
   `start`, `stop`, `restart`), checkboxes, state-changing three marked "Changes the container". No
   exec, shell, create/remove, network or raw-proxy operation exists, and a test asserts the count.
   Creating with *n* operations adds *n* rules (one stored per operation) and the review box says so
   ("This adds 2 rules" + one sentence each); the server must apply all or none (§8).
   Editing fixes subject and operation.
4. *Container*: endpoint stated and fixed ("a rule can never reach another"). **Container name** plus
   "Match as a pattern" (`*`, `?`); an exact name containing pattern characters is refused until marked
   as a pattern. **Start from a running container** fills name and Compose labels from the inventory.
5. *Identity checks (recommended)* disclosure: Compose project, Compose service, image pattern, pin to
   one image digest, pin to one container ID (64 hex). An invalid value opens the disclosure and focuses
   the field.
6. *Limits*: "Most log lines per request" (1–10,000) only when Read logs is ticked; "Longest stop
   timeout" (1–300 s) only when Stop or Restart is. Unticking the operation drops the ceiling.
7. *Guardrail summary*, live: **Pinned / Guarded / Name only / Pattern / Broad**, each with one sentence
   ("Name only: A different image started under this name would match too."). Broad Allow shows the
   acknowledgement checkbox, required to save.
8. *Which containers does this match* (**Check matches**): sends the **normalised** selector once;
   results list name, image, short id, Compose labels. Editing any selector field marks the result
   *stale* and hides it ("The selector changed since the last check"). Empty result: "No container
   matches yet… the rule can still be saved and will show as Inactive · target missing". `unavailable`:
   "Matches can't be checked right now"; still saveable. The preview is explanatory only; every request
   is evaluated again when it arrives.
9. Submit validates all fields, lists **every** problem, moves focus to the first, and sends nothing
   until clean.

## 6. Outcome → presentation mapping for the container (P1.17.2)

The coder maps HTTP outcomes to `Load` / `Mutation`; the screens never see a status code.

| Server outcome | Screen input |
| --- | --- |
| 200/201/204 on a command | `Mutation.done` with a sentence built from names already shown |
| 400 / validation | `rejected: invalid` (field errors shown by the screen itself from the same rules) |
| 401 | not a screen state: the signed-in frame shows "Your session ended" |
| 403 (denied, not admin, no step-up, authority changed) | `Load.denied` for a list; `rejected: denied` for a command, **except** a step-up requirement, which opens `StepUpGate` |
| 404 | `rejected: not_found` |
| 409 | `rejected: conflict` |
| 429 | `rejected: rate_limited` |
| 503 on a **mutation** | `rejected: outcome_unknown` (never `invalid`, never "nothing changed") |
| 503 / network on a **list** | `Load.failed` |
| network failure on a mutation | `outcome_unknown` as well: the request may have reached the server |

After any `done` or `outcome_unknown` the container refetches the list; the screens hold no copy of
server state besides the editor draft.

## 7. Accessibility, keyboard and responsive behaviour

* **Landmarks and headings.** One `main`, one `h1` per page, no skipped level inside any specimen
  (asserted for every screen and every gallery specimen in both themes).
* **Names.** Every input has a label; every row button's accessible name carries its object ("Disable
  sample-sam", "Edit: Allow agent …"), so no two buttons read the same. Hints are associated with
  `aria-describedby`; errors with `aria-invalid` and `aria-describedby`, and are announced.
* **Focus.** Submit failure focuses the first invalid field (opening its disclosure first). A new
  outcome takes focus. Opening a confirmation focuses its group; Escape or Cancel returns focus to the
  button that opened it (`returnFocusId`). No control disappears under focus without focus moving
  somewhere meaningful.
* **Keyboard.** Everything is native: Tab/Shift-Tab order is DOM order; arrow keys move within a radio
  group; Space toggles a checkbox; Enter/Space toggles a `<summary>`; Enter submits a form; Escape closes
  a confirmation.
* **Where a failed submit lands.** The editor applies focus *after* the render that shows the messages,
  then scrolls the field to the centre of the window, instantly. Engines disagree about where a plain
  focus scroll leaves a field: WebKit left it at the very top edge, under the 64px sticky header
  (measured: field top −0.5px, header bottom 64px). With the centred scroll all three engines put it at
  about 480px from the top at 1280 and 390 px widths. Instant means there is no animation for reduced
  motion to remove. `html { scroll-padding-top: 6.5rem }` (in `style.css`) additionally keeps any other
  focus or anchor scroll clear of the header.
* **Targets.** Controls are at least 44 px high (`min-h-11`); row action buttons wrap rather than clip.
* **Responsive.** Rows stack below `lg`; radio groups and the editor are single-column below `sm`; no
  horizontal scroll was found at 320, 390, 768 and 1280 px (§10).
* **Motion.** The chevron turn and colour fades are removed by the global `prefers-reduced-motion` rule.
* **Both themes** use tokens; contrast is checked by P1.16's token test and by the browser audit in §10.
  No colour pair was invented here.
* **CSP.** No inline style, image, remote or `data:` URL; production CSP is `default-src 'none';
  script-src 'self'; style-src 'self'; …`. The browser runs below used that header.

## 8. Handoff to P1.17.2 (the coder)

### 8.1 Props and state contract

Exact types are in `src/screens/policy/contract.ts`; the screens are `UsersScreen`, `GroupsScreen`,
`AgentsScreen` (from `agentIdentity.tsx`) and `RulesScreen` (which renders the editor). Each takes
`load`, `mutation`, `pending`, the lifecycle `actions` the backend supports, optional `rulesHref`, and
callbacks that report **intent only**:

```ts
onCreate({ username })                      // users
onCreate({ name })  onAddMember({ groupId, kind, memberId })  onAskRemoveMember(groupId, kind, memberId)   // groups
onCreate({ name, owner: { kind: 'user' | 'group', id } })  onTransferOwner({ agentId, owner })            // agents
onSubmit(draft: RuleDraft, editingId | null)  onPreview(selector: SelectorDraft)  onEdit(id)  onNew()    // rules
onAsk(action, id)  onCancel()  onConfirm()  onRetry()                                                      // all
```

`pending` is what the container wants confirmed; the screen renders the named confirmation and calls
`onConfirm` / `onCancel`. The container owns the single source of truth for `pending`, `editor`,
`mutation` and `preview`.

### 8.2 Data the server must supply (proposals; none exist as API yet)

Verified by reading `internal/auth`, `internal/authz`, `docs/authorization.md` and
`migrations/00001_initial.sql`. **The admin API for these screens was not in the repository when this
was written**; the shapes below are what the screens need, not a contract the server has.

* Users/groups/agents with `state` (`active | disabled | quarantined`), counts, and a **`Removal`** the
  server decides (blockers named, from the `ON DELETE RESTRICT` relationships).
* Rules with `state`, `limits`, and a **`TargetStatus`** per rule from the endpoint's container list
  (`Authorizer.InspectEndpointPolicyTargets`). `unknown` when the backend cannot be inspected.
* `EndpointView.safety` (`verified | unverified`) and an optional `inventory` (null when it cannot be
  listed) that **excludes Mandatary and its peers**.
* A preview endpoint that takes the **normalised** `SelectorDraft` and returns matching `InventoryRow`s.
* Rule create: one request, **all or none**, for *n* operations; update by id; enable/disable/delete by
  id. The server re-validates everything (`acknowledgedBroad` is a UI hint it must not trust) and
  rejects an operation outside the six, a self-targeting selector, a disabled subject and an owner that
  is not exactly one of user/group.
* Agent create with exactly one owner; owner transfer (accountability only; **must not** change any
  rule or grant); lifecycle actions. Disable agent must revoke its tokens and cut its streams.
* A single policy administrator: no screen offers to create, promote or add another.

### 8.3 What the container must do

* Own fetch, CSRF, step-up and the §6 mapping; refetch after every command.
* Add the four exact routes to `web/assets.go` and the "Policy" nav items for the administrator only.
* Relabel P1.16's "Agents" nav item "Agent tokens" (§4).
* Keep `actions` honest: pass only lifecycle actions that work end to end.
* Never log or store draft contents; the editor draft lives in component state only.

### 8.4 Security assumptions to validate before integrating

1. The server refuses every list and command for a non-administrator and for a session without a fresh
   second factor, independent of anything the UI hides. (The screens assume it; they cannot prove it.)
2. A rule's subject, selector, operation and limits are validated server-side to the same documented
   limits as `selector.ts`; the UI's early feedback may be stricter or looser than the server's and the
   server's answer wins.
3. **A 503 after a durable commit is indistinguishable from a failed write** (`unavailable` for a failed
   policy notification). If the coder can make the two distinguishable, `outcome_unknown` can be refined;
   until then it must be used for every mutation 503.
4. Owner transfer and membership removal take effect for open streams the same way disable does, or the
   copy "the agent keeps exactly the access it has now" / "access is cut" must be adjusted.
5. Preview results come from the same endpoint the rules apply to, and contain no container that the
   evaluator would refuse as self/peer.
6. `quarantined` rules and memberships never grant or deny anything; restore approval is P1.18.

### 8.5 File boundaries and conflict hotspots

New files are all under `src/screens/policy/`, `src/ui/{Choice,ConfirmPanel,Disclosure}.tsx` and
`src/gallery/{PolicyGallery*,policyFixtures.ts}`. Modified existing files: `src/gallery/Gallery.tsx`
(one route), `src/ui/Icon.tsx` (icons `ban`, `users`, `edit`, `box`, `bot`, `chevron`), `src/ui/index.ts`
(exports) and **`src/style.css`** (one rule: `html { scroll-padding-top: 6.5rem }`, §7). That last one is
the only change to a shared P1.16 file and it affects every page (focus and anchor scrolls stop short of
the sticky header); the coder may keep or drop it, and a source test guards it. Nothing else in P1.16 was
edited. P1.17.2 will likely touch `web/assets.go`, `App.tsx` and the nav helper; this contribution does not.

## 9. Outstanding issues (honest list)

1. **No admin API exists to build against**, so every wire shape in §8.2 is a proposal. The coder owns
   mutation semantics, authorization and the real data.
2. The editor preview and guardrail classification **mirror documented behaviour**; they are not the
   evaluator and may disagree with it on edge cases. The server's verdict wins.
3. **Native `<select>` under strict CSP in Playwright WebKit** (carried from C3 observation O3): a
   `style-src-attr` violation is reported for any bare `<select>` in that build. This work uses native
   selects in the rule editor, group member picker and agent owner picker, and the WebKit run reproduced
   it on exactly the views that contain a select (G-b, A-b, R-d, E-a, E-c, and the shell views for rules,
   groups and agents) and on none of the others (the Users page has no select). Chromium and Firefox
   reported nothing. Every control worked in WebKit (all 14 behaviour checks passed), so the effect
   observed is a console/CSP report, not a broken control. Whether real Safari does the same is
   **unverified**, and the choice to use native selects (D-P117-3) is kept on the strength of keyboard
   and assistive-technology behaviour; replacing them would need a custom widget.
4. Contrast is verified by tokens and by the shared structural audit, which **skips non-rgb colours**
   (P1.16 finding L4). It is not a WCAG conformance claim and no external accessibility scanner was run
   (O3 of P1.16: no axe-core is approved).
5. The shared keyboard audit lists controls inside a *closed* `<details>` as unreachable. The browser run
   opens every disclosure before auditing, and tests the closed → open path separately by keyboard.
6. Loading and "checking" specimens are busy by design; the shared audit waits for `aria-busy` to clear,
   so the run drops that attribute to audit their structure. Their busy behaviour is covered by unit tests.
7. Large lists are not paginated or virtualised. The gallery has 9 rules; a real installation could have
   many, and filtering is client-side over whatever the server sends. A pagination contract is
   a proposal for P1.17.2 if the server paginates.
8. A group's own Deny rules and agent-via-group inheritance are *described* in copy but the screens do
   not compute "effective access" for a subject. That would require the evaluator and was out of scope.
9. No automated screen-reader pass. Names, roles and focus order were asserted structurally only.

## 11. Decision log

| ID | Decision | Why |
| --- | --- | --- |
| D-P117-1 | Screens are stateless; draft state exists only in the editor form | Containers own HTTP, CSRF, step-up; a screen cannot decide permission |
| D-P117-2 | `outcome_unknown` for every mutation 503 or network failure | A 503 may follow a durable commit |
| D-P117-3 | Native select/radio/checkbox/details only | Keyboard and AT behaviour defined by the browser; no dependency |
| D-P117-4 | ConfirmPanel for every destructive or authority-changing action | One keyboard and focus model (D-CONFIRM-1) |
| D-P117-5 | Broad Allow needs an explicit tick; broad Deny does not | Risk is in granting more, not in blocking more |
| D-P117-6 | Owner is user XOR group, active accounts only | Matches the schema and avoids a state the server must refuse |
| D-P117-7 | Missing and unknown targets stay visible, `unknown` is never shown as a match | Hiding them would let a grant look healthier than it is |
| D-P117-8 | Agent tokens are linked to, not shown | Reveal-once belongs to P1.16's `SecretReveal` |
| D-P117-9 | Nav label "Agents" (policy) vs "Agent tokens" (P1.16) | Two entries may not share a name |
