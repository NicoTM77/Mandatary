state contract that P1.16.2 (junior), P1.16.3 (setup/login) and P1.16.4 (factors/recovery/

## 3. Design language

**Direction.** A calm, instrument-panel look for people making security decisions: quiet
graphite-teal neutrals, one accent (harbour teal), opaque surfaces for everything that is read
or filled in, and **one memorable element**: the dashed amber *reveal-once* panel (§8), the only
place the interface raises its voice. Apple's principles are applied, not imitated: clarity and
deference (content first, restrained chrome), consistency, direct feedback for every state, and
accessibility as a design input. Liquid-Glass-style translucency is used only on the sticky shell
header (`bg-surface/92 + backdrop-blur`) where it aids orientation while scrolling; forms, tables,
secrets and alerts are always opaque.

### 3.1 Tokens (semantic; both themes; `src/style.css`)

Use the semantic utility (`bg-surface`, `text-muted`, `border-line-strong`), never a hex and never
`dark:`. The values are asserted for WCAG contrast in **both** themes by `theme-contrast.test.ts`
(26 pairs × 2 themes).

Type: system stacks only (the CSP forbids web fonts). Body 15 px / 1.5, **controls 16 px** (no iOS
focus-zoom), headings `text-wrap: balance`, codes and tokens monospace with tabular figures.
Scale used: 12 (badges) · 14 (hints, captions) · 15 (body) · 16 (controls) · 18 (panel title) ·
24/28 (page title). Radii: control 8 px, panel 14 px, pill 999. Spacing: 4-pt grid; panel padding
20/24 px; field rhythm 16 px. Minimum interactive height 44 px (`min-h-11`).

Colour is never the only carrier of meaning: every tone is paired with an icon **and** text
(`Alert`, `Badge`, step state, assurance label).

### 3.2 Theme behaviour (D-THEME-1)

First paint follows `prefers-color-scheme` and tracks OS changes; the toggle overrides **in memory
for the page view only**. No `localStorage`, `sessionStorage` or cookie is written, which keeps the
original card's "no secret/storage leakage" check trivially verifiable (`App.test` and the UI tests
assert zero storage writes). Trade-off: a reload returns to the system theme. A persisted
preference is a separate decision. Theme is applied as `data-theme` on `<html>` so scrollbars and
native controls follow it (`color-scheme` is declared per theme).

### 3.3 Motion

State changes use 150 ms colour transitions only. The one animation is the busy spinner, always
accompanied by a visible "Working…" label. `prefers-reduced-motion: reduce` collapses all
animation/transition to ~0 (verified in Chromium).

## 4. Shell and shared patterns

* **`AdminShell`** (P1.16–18): skip link → sidebar `nav aria-label="Primary"` (groups, `aria-current="page"`,
  collapses to a *Menu* disclosure button below `lg`, `aria-expanded`/`aria-controls`, Escape closes and returns
  focus) → sticky session strip (username, **server-derived** assurance badge "Multi-factor verified" /
  "Password only", optional freshness note, theme toggle, Sign out) → `main#main-content`. It performs no routing,
  fetching or authorisation; items a user may not use are *not passed in*, and the server enforces regardless.
  Only items that exist are listed (D-NAV-1).
* **`CenteredFrame`**: pre-session frame for setup/login/recovery (no navigation).
* **`Panel` / `PageHeader` / `DetailRow`**: opaque content surfaces; heading level is explicit so the page outline is h1 → h2 → h3.
* **`Alert`**: `info/success/warning/danger`, icon + title + body + actions. Danger defaults to `role="alert"`,
  others `role="status"`, `role="none"` for content present at load. Alerts are focusable by script
  (`tabIndex -1`).
* **`Badge` / `SyntheticBadge`**, **`Steps`** (position as text "Step 2 of 5", `aria-current="step"`).
* **Inline confirmation** (D-CONFIRM-1): destructive actions open an in-place `role="group"` that **names the
  object** ("Remove Desk key?"), states the consequence and notification effect, and offers "Remove <name>" /
  "Keep it". No modal, no undo promise. Destructive buttons are outlined-danger, never the default focus.
* **Step-up panel** (D-STEPUP-1): see §7.4. **Reveal-once** (D-REVEAL-1): see §8.

## 5. Form, autofill, paste and password-manager behaviour (F3)

Applies to every form (`useRequiredForm` in `screens/shared.tsx`; asserted in `screens.test.tsx`):

1. A real `<form method="post" noValidate>` with **no `action`**; the handler **always** calls
   `preventDefault()`. A credential can therefore never reach a URL query string, and the CSP
   (`form-action 'none'`) would block a native submit anyway. Never `GET`.
2. **Uncontrolled inputs**: values are read once, at submit, with `FormData`. A password, code or token never
   lives in React state, context or props. Password fields are blanked when the screen enters a rejected state;
   username is kept; code/token fields are blanked on rejection too.
3. Empty required fields show an inline "Enter your password." linked with `aria-describedby`/`aria-invalid`, focus
   moves to the first, **no request is made**. This is convenience only; the server verdict is authoritative.
4. While a request is in flight inputs become `readOnly` (not `disabled`) and the button gets `aria-busy` +
   `aria-disabled` (not `disabled`), so focus is not dropped and repeat activation/double-submit is swallowed.

| Field | Attributes (exact) | Why |
| --- | --- | --- |
| Sign-in username | `name=username autocomplete=username autocapitalize=none autocorrect=off spellcheck=false` | manager association |
| Sign-in password | `name=password type=password autocomplete=current-password` | manager autofill |
| New password (setup / reset) | `name=password autocomplete=new-password` | manager offers to generate/save |
| Step-up password | same, plus a visually hidden read-only `username` input with `autocomplete=username`, `aria-hidden`, `tabindex=-1` carrying the **non-secret** account name | managers file it under the right account |
| TOTP code | `inputmode=numeric autocomplete=one-time-code enterkeyhint=go`, **no `maxlength`, no `pattern`**, single field | paste of "123 456", platform code fill and screen readers all work; container strips spaces/hyphens before sending |
| Mailed address proof | `autocomplete=one-time-code inputmode=text`, same rules | |
| Saved recovery code, setup token | `autocomplete=off` + `data-1p-ignore data-lpignore data-bwignore`, `spellcheck=false` | never offered for save/autofill |
| Notification address | `type=email autocomplete=email autocapitalize=none` | |

Password specifics (D-PW-1): **paste is never blocked** (no `onPaste` handlers anywhere; asserted); no composition
rules, no strength meter and no length counter in the UI (the server contract decides; a UTF-16 `.length` or
`normalize()` count is explicitly *not* an authority); no confirm-password box; a **Show password** toggle
(`aria-pressed`, constant label) lets people verify instead, and it re-masks on submit. Visible guidance:
"Use 8 to 128 characters. Password managers and pasting are welcome. We check it against common and
previously exposed passwords when you continue." plus the endpoint-representation note ("accents and emoji can
be typed differently on other keyboards") required by `docs/password-authentication.md`.
Server `password_rejected.guidance` is a fixed string rendered **as text on the password field** (never HTML;
asserted with a `<b>` payload).

### 6.2 Login (⚠ no routes yet; presentation rules are firm, wire shapes are the coder's)

`denied` is **the one outcome** for unknown user, wrong password, exhausted factor and an account-level wait
(generic 401 parity; the password contract forbids an account-existence or factor-state signal). Copy:
"The username or password is incorrect, or sign-in is paused after too many attempts." `rate_limited` is for
connection-level admission only. `Next` steps (`totp`, `webauthn`, `no-mfa`) come from the server in order and
are never computed by the UI; "Continue with password only" appears **only** if `no-mfa` is present, with the
lower-assurance explanation. The 5-minute preauth ends in `expired` → "Start again". Logout failure (503) keeps
the session visible (the server keeps the cookie) and shows an error; the UI never claims a logout it did not
get.

### 7.1 Slice 1 — setup and login (P1.16.3)

Sequence: `/setup` → **token** → **account** (username, password, 1–4 addresses) → **addresses** (prove ≥1) →
**authenticator** (key shown once, confirm code) → **finish** → "Go to sign in" → **password** → **factor** →
session. The setup session shows its fixed deadline on every screen (`SetupClockNotice`: ends in N minutes;
≤5 minutes becomes a warning; expiry becomes a blocking danger state with the exact host remedy). The deadline
never extends with activity and the UI does not imply it does. The mail-relay-unconfigured state blocks the
account step with an operator explanation instead of a doomed form (the first administrator cannot be completed
without an address proof). The emergency `mfa_reset` ceremony reuses the same screens: username read-only,
password step only when `replace_password`, no address step.

### 7.2 Slice 2 — factors, recovery, step-up (P1.16.4)

`Account security` page (shell view in the gallery): notice health banner → sign-in methods → recovery codes →
notification addresses. Adding/removing any factor, address or recovery list needs fresh assurance: the
container catches `step_up_required` and shows `StepUpPanel` in place. Removing the last second factor is
allowed by the server only under its own rules; the UI never decides, it names the consequence in the confirm.

### 7.3 Notification addresses (F7) — approved multi-address behaviour

Setup accepts **1–4** addresses and requires proof of control of **≥1** (`SetupAddresses`: "N of M confirmed. You
can continue"). After setup, the screen enforces what the lifecycle doc requires: **at least one confirmed address
always remains** (the last confirmed address has its Remove disabled with the reason shown, never merely greyed);
**two or more are recommended** (info banner when only one is confirmed); the list is capped (`maxAddresses`,
default 4; the post-setup cap is a backend decision the coder must confirm); an address is **not used until
confirmed** (status badge "Not confirmed", proof step with `one-time-code` input and "Send a new code"); add is
disabled with an explanation when the relay is not configured. Every change tells the person which other
addresses will be notified (the old/new-address alerts are P1.16's narrow ceremonies per
`authenticator-lifecycle.md`). Rejections: `denied` ("needs fresh verification or the address can't be used"),
`wrong_code`, `rate_limited`, `unavailable`.

### 7.4 Step-up (F9) pattern

An inline interstitial, **not** a modal (D-STEPUP-1). Reason: step-up is a fresh sign-in that issues a
*successor* session, rotates the secret and CSRF token and discards ceremonies begun under the old session
(`docs/sessions-browser-security.md`); auto-replaying the blocked request would replay a request authorised by
the previous session. The container therefore (1) discards pending ceremonies, (2) adopts the new CSRF token,
(3) does **not** resend the request, and the panel's `verified` state says "Your earlier request was not sent.
Repeat <action> now." Methods: AAL1-only account → password only; AAL2-capable → password + TOTP, or WebAuthn
UV. If the account has no usable factor the server answers `assurance_unavailable` and the panel shows the
no-retry recovery state naming `mandatary recovery reset-mfa`. Freshness is 15 minutes (inclusive); the shell
may show "Verified N minutes ago".

### 7.5 Security-notice failure states (F8)

Aggregate counts only (`auth.NoticeStatus`); **no recipient, SMTP diagnostic or message content ever appears**.
Severity order: **protective > 0** (danger: a security change took effect but no notice could be stored;
operator must notify by another channel; *no retry offered*) → **unknown/unreadable** (warning; never shown as
healthy) → **failed/bounced/quarantined** (warning with itemised counts; retry offered only when `failed > 0`
and the viewer can repair) → **pending** (info, "normal for a moment") → **healthy** (success, silent on load).
Security transitions are transactionally tied to durable notice intent, so a notice failure is a *delivery*
problem, never a reason to claim a change did not happen.

## 8. Reveal-once treatment (F10, F4 key, F6 codes)

`SecretReveal` is the single component for agent tokens, TOTP keys and recovery codes. Treatment: a dashed
amber panel (`warn`), the only high-emphasis element in the product; heading names the secret; the line "This is
the only time it will be shown. Reloading or leaving this page removes it for good."; consequences (expiry,
overlap) in `intro`; the value in a monospace block (`translate="no"`, select-all on click, wraps, never
truncated); **Copy** (clipboard failure → manual-copy instruction); a **two-step dismissal** (acknowledge
checkbox → "Hide the token"); for TOTP keys no acknowledgement is required and the container removes the key
when the first code is proven.

Leak-prevention rules (asserted in `ui.test.tsx` / `screens.test.tsx` for attributes, title, URL, storage,
live region and DOM removal; React keys, history state and `console` output are guaranteed by construction
and review only, so P1.16.3/4 must add real-flow assertions for them):

* The secret is the **text content of one element** only: never an attribute, `id`, class, `data-*`, `aria-label`,
  `title`, `document.title`, URL, history state, `localStorage`/`sessionStorage`/cookie, React key (index keys are
  used), or `console` output.
* The live region says only "Copied to clipboard." — it never contains the secret.
* "Hide" **removes** the node (not `display:none`), renders a secret-free notice, calls `onDone` once; the
  container must drop its own reference in `onDone`. After hiding, `document.body.innerHTML` does not contain the value.
* Focus moves to the panel on mount so screen-reader users land on the warning first.
* The list of credentials (`AgentCredentials`) shows only a short non-secret display id, status and dates.
* Browser-history/bfcache: containers must keep the secret out of any state that survives navigation, and the
  response must be `Cache-Control: no-store` (already true). P1.16.3/4 test: back/forward after hide must not
  restore the secret.
* Gallery fixtures are unmistakably fake and **not shaped like real secrets** (`SYNTHETIC-…`, not base32, not
  43-char base62), asserted by `Gallery.test.tsx`, so secret scanners stay quiet.

## 10. Handoff

### 10.1 Props and state contract

The **exact** contract is the TypeScript in `src/screens/contract.ts` (screens, states, callbacks, with the
secret-handling rules in its header) and the exported prop types in `src/ui/*.tsx` (`ButtonProps`, `TextFieldProps`,
`PasswordFieldProps`, `CodeFieldProps`, `AlertProps`, `SecretRevealProps`, `AdminShellProps`, `PanelProps`, …).
Summary of the rules that matter to integrators:

* Screens are **stateless**: `(state, data, callbacks) → UI`. Containers own fetching, cookies, CSRF, timers,
  routing, retries and every security decision. A screen never calls `fetch`, touches storage, or interprets an
  HTTP status.
* Callbacks receive plain values once, at submit (`{ password }`, `{ code }`, `{ token }`).
* Reasons are presentation reasons (§6), never raw server text, except `password_rejected.guidance`.
* Secret-bearing state (`seed_shown.seed`, `reveal.codes`, `reveal.token`) must be **dropped by the container as
  soon as the state leaves** the revealing state or `onHidden` fires.
* `AdminShell.account.assurance` is the server's label. The UI never computes, upgrades or persists it.

### 10.3 Security assumptions the coder must validate before integrating

1. Setup `exchange` really returns the same `401 invalid_token` for wrong, expired and replayed tokens (UI copy assumes it).
2. `403 denied` on `addresses/confirm` and `totp/confirm` cannot be disambiguated from a wrong code (UI copy covers both).
3. The TOTP `begin` request's accepted `algorithm` value(s) (the handler echoes the string; docs say SHA-256) and that the begin response is the **only** time the seed is available; whether a lost seed can be restarted at all (`onRestart` is optional for this reason).
4. Login responses keep generic 401 parity for unknown/wrong/exhausted/throttled cases; `recovery_required` is only offered if it is also account-independent.
5. The `Next` vocabulary (`totp`, `webauthn`, `no-mfa`) and that `no-mfa` is never present for administrators or required-MFA accounts.
6. Step-up success rotates the CSRF token; pending enrolment/WebAuthn ceremonies are gone; the old CSRF token fails (second-tab case).
7. `SessionInfoHandler` fields are the only assurance inputs the shell displays; none is client-asserted.
8. CSP widening is limited to `connect-src 'self'`; `form-action 'none'`, `style-src 'self'` stay; the exact-route allowlist adds no SPA wildcard; `/setup` remains 404 when no generation is live (the SPA shell may load, the API stays closed).
9. Back/forward/bfcache never restores a revealed secret; responses stay `no-store`.
10. Clipboard use is a user-initiated copy only; no secret is ever written to logs, `console`, error boundaries or crash reports (add a console-capture assertion to the real flows).
11. The post-setup address service enforces min-1-confirmed, the `notification-address-change` freshness gate, proof-before-use, old/new-address notices and the cap — the UI is a presentation of those rules, not their enforcement.

### 10.4 Outstanding issues (honest list)
