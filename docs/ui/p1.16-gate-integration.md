## 2. What the gate changed (tests, plus one small adapter fix)

* `web/tests/engine.mjs`: engine selection for the browser scenarios. `MANDATARY_BROWSER_ENGINE` is
  `chromium` (default), `firefox` or `webkit`; `MANDATARY_VIEWPORT=WIDTHxHEIGHT` (default `1280x900`, a phone run is
  `390x844`). Chromium maps the one synthetic host (`example.invalid`) to loopback with a resolver rule.
  Firefox and WebKit have no such switch, so they are pointed at a loopback `CONNECT` tunnel that carries **only**
  `example.invalid` on a port of 1024 or more to `127.0.0.1` and refuses everything else (a second, engine-independent
  egress block; the page-level request allowlist stays in force). `scripts/browser-engine-tunnel.test.mjs` tests the
  tunnel (7 refused destinations, one carried); a mutant that drops the host check fails it.
* `internal/auth/{admin,security}_ui_browser_test.go`: `MANDATARY_BROWSER_ENGINES` (comma list, default `chromium`;
  an unknown name fails) selects which engines the existing Go-driven scenarios run on. Test names are now
  `engine/scenario/scheme`. `make browser-test` is unchanged and still runs Chromium only (as CI does).
* `web/tests/a11y-audit.mjs` made engine-independent after Firefox exposed two real test defects:
  the Tab walk now starts from a focusable anchor at the top of the document (Firefox keeps the previous sequential-focus
  start after `blur()`), and colours are audited at rest (finite CSS transitions are awaited; the 150 ms colour fade
  was being judged mid-fade after a back navigation). A contrast violation now names the colours, class and size
  (never page text).
* The theme check waits for the effect that applies the theme (a slower engine lost the race); the admin script prints
  the real failure before closing the browser; the phone-sized viewport opens the Menu before using the navigation.

* Two CodeQL findings raised by the hosted run on the first push were fixed at the source, not dismissed:
  * `js/disabling-certificate-validation` (`web/tests/admin-ui-lib.mjs`): the raw HTTPS client no longer sets
    `rejectUnauthorized: false`. The Go test hands the fixture server's own public certificate to the script
    (`MANDATARY_FIXTURE_CA_PEM`) and the client trusts exactly that certificate (checked against the name the
    certificate carries). A second server presenting a different certificate is refused (`DEPTH_ZERO_SELF_SIGNED_CERT`).
  * `go/weak-sensitive-data-hashing` (`internal/auth/session_service.go`, a false positive: the hashed value is the
    random 256-bit session secret, not a password; CodeQL tainted it because the login result comes from a function
    named `PasswordLogin`). The password login adapter no longer feeds the freshly issued session secret into a second
    service lookup: `Sessions.PasswordLogin` now returns the account's usable authenticator-app identifiers
    (random, non-secret record ids, already loaded in the same transaction) in `LoginResult`, and the adapter
    reads them from there. Same response, one lookup fewer; `TestAccountSecurityHTTPTOTPLifecycle` kills a mutant that
    drops the list.

* The hosted Baseline job failed once in vitest (`setup … server password guidance … password is cleared`, a
  timing-dependent assertion that passed locally). The cause was real: a rejected password was blanked by a passive
  effect, so for one commit the guidance was on screen while the rejected password still sat in the field. The
  shared form hook now blanks in a layout effect (same commit), and
  `the rejected password is already blanked in the commit that first shows the guidance` observes the DOM at the
  moment the guidance first appears (RED before the change in both themes, GREEN after).

No dependency, workflow, lockfile or `.agents` change. The only non-test code changes in this gate are the
`LoginResult` field above (`session.go`, `session_service.go`, `login_http.go`) and the layout effect in
`web/src/screens/shared.tsx`.

## 4. Limits that remain (not hidden)

* **Key (WebAuthn) flows are Chromium-only.** Playwright exposes the virtual authenticator over CDP only, so security-key
  enrolment/sign-in/step-up/removal with a real CTAP2 ceremony is evidenced on Chromium; the Go service tests cover the
  server side for every engine. Firefox and WebKit have no browser-level key evidence. The scenario is not run (not
  skipped silently) on those engines.
* **Playwright's WebKit is not Safari**, and no Safari >=26, branded Chrome/Edge, Firefox ESR, real password manager,
  real screen reader (NVDA, JAWS, VoiceOver, TalkBack) or physical authenticator was available or run. SUP-04
  branded-browser/manual-device evidence remains open for the owner.
* **No axe-core.** A scanner engine is a new dependency (licence review needed; axe-core is MPL-2.0, to be confirmed
  by the owner), which this card is not authorised to add. The accessibility evidence is the in-repo structural audit:
  language, title, main landmark, one `h1`, heading order, control names, labels, duplicate ids, ARIA references, image
  alternatives, hidden-focusable, positive tabindex, WCAG 1.4.3 contrast on resolved colours, a real keyboard Tab walk with
  a visible-focus check. It cannot judge reading order, screen-reader output, zoom/reflow to 400%, text spacing,
  reduced-motion, touch-target size, or background-image contrast. It is evidence of "no unexplained serious/critical
  violation found by this audit", not a conformance claim; whether it satisfies the owner's accessibility bar, or
  whether to add axe-core, is an owner decision.
* Firefox and WebKit need system libraries that this host lacked. The runs used Debian trixie packages unpacked into the
  scratch area (no system change) and a software GL stack; they were not run in CI, which only installs and runs Chromium
  (`make browser-install`, `make browser-test`). Adding Firefox/WebKit to CI is a workflow change and is the owner's
  decision.
* Playwright on Linux focuses buttons with Tab; macOS Safari by default does not. The keyboard walk therefore does not
  prove Safari's default keyboard behaviour.
* The earlier slice limits stand: TOTP offers SHA-256 (apps that support only SHA-1 may reject it); security keys have no
  stored name; ES256 only; own-session management and general notification features are later phases.
