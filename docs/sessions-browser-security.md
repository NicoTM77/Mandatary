# P1.08 sessions, browser security and step-up

This is the P1.08 component contract and test crosswalk. It records what the code
actually does and which executable tests exercise it. It is **not** a NIST, FIPS,
product, browser or deployment conformance claim: the approved
[NIST mapping](../nist-authentication-mapping.md) stays authoritative, every
`N63B4-*` row keeps its other owners, and exact-head command results and CI are
recorded on the original Kanban card / draft PR, not here.

**What P1.08 itself delivers.** `Browser` is middleware plus a policy registry.
The P1.08 tests register their own routes; the product mounted none at that point.
**Update (P1.16.3, local contribution to P1.16, not independently reviewed):**
`internal/auth/login_http.go` now registers the slice-1 account routes on this
boundary with explicit policies when the server has a trusted origin and a notice
relay: `POST /api/v1/login` (`RequireNone`), `POST /api/v1/login/totp` and
`POST /api/v1/login/no-mfa` (`RequirePreauth`), `GET /api/v1/session` and
`POST /api/v1/logout` (`RequireSession`). Step-up, security-key login and the
factor/recovery routes remain slice 2 (P1.16.4) and are not mounted. See
[the P1.16.3 integration record](ui/p1.16.3-setup-login-integration.md). Setup/recovery
sessions are P1.09, agent bearer adapters are P1.14, own-session visibility UI is
Phase 3, backup/agent-credential/policy mutations are P1.10/P1.18/P1.17, and
trusted TLS topology evidence is P1.19/20.

## Server-bound evidence (acceptance: no client upgrade)

* The only client-controlled session input is one 256-bit opaque cookie secret.
  Assurance, methods, authentication time, phishing resistance, credential and
  session generation are read from the persisted row and the live
  `installation_control` row; the API has no parameter through which a caller
  could assert them. Headers, query/body fields, extra cookies, `Authorization`
  and forwarded headers are never consulted.
* A persisted label is trusted only when `evidenceBacked` finds live, correctly
  owned factor rows bound **before** the authentication time. A forged
  `achieved_assurance`/`methods` row without matching factors is denied.
* Labels: `password-only` (lower assurance, never AAL2), `aal2`, and `preauth`
  (a five-minute login capability, not a session). Methods are `password`,
  `password+totp`, `password+webauthn` (not producible: only UV assertions are
  accepted) and `webauthn-uv`.
* AAL2 is produced only by password+TOTP (`methods=3`) or a signed UP+UV WebAuthn
  assertion (`methods=8`, phishing resistant). Password alone, TOTP alone (no
  preauth), UV=false WebAuthn, recovery, setup and agent credentials cannot. The
  recovery/setup purposes are rejected by `Authenticate`; recovery completion and
  setup issue no session in this card.
* Account policy is re-evaluated on every request: administrators and
  `mfa_requirement` `required`/`webauthn` can never hold a password-only session;
  `webauthn` accounts accept only UV WebAuthn (TOTP cannot satisfy or step up).
  Role, policy, compromise, factor revocation, user disable and generation changes
  therefore end copied cookies immediately. The shared authorizer's
  `VerifyPrincipal` is driven through the same mutations and must agree.

## Lifecycle

1. `PasswordLogin` → real `Service.Prove` (shared throttles, comparable work).
   Optional-MFA account with no second factor and a ≥15-code-point password gets a
   labelled password-only session. Otherwise a **preauth** capability plus the
   permitted next steps (`totp`, `webauthn`, and `no-mfa` only if policy allows
   password-only). Required MFA without a usable factor is denied, never weakened.
2. `LoginTOTP` / `LoginWebAuthn` verify through the real services, then in one
   durable control transaction consume the preauth and issue a **new** secret and
   ID (no fixation). Concurrent completion of one preauth yields one session.
3. `Authenticate(secret, activity)` is read-only except an idle touch at most every
   15 s; the touching statement itself carries the absolute and idle predicates, so
   a row that expired between the read and the write is never revived. `activity=false` (polls/streams) never extends idle; idle resets only the
   30-minute clock, never the 12-hour overall limit. A touch that skips can only
   shorten, never extend, idle life.
4. **Step-up is re-authentication.** It verifies new proofs and issues a
   *successor* session carrying only the new evidence, revokes the predecessor in
   the same transaction, rotates secret/ID/CSRF token and resets both clocks. It
   can only raise assurance/phishing resistance (a phishing-resistant session
   cannot be "refreshed" with TOTP; a password alone never refreshes an
   AAL2-capable account). A failed proof changes nothing. Pending enrollments and
   WebAuthn ceremonies are bound to the predecessor's ID, so a step-up mid-ceremony
   requires restarting it.
5. `Logout` durably revokes before the cookie is cleared; a storage fault is a
   503 that keeps the cookie, never a claimed logout.
6. At most 32 live rows per user (oldest, preauth first, revoked on issue). A
   client without the password cannot create any row.

Defaults and ceilings: absolute 12 h, idle 30 min, step-up 15 min. Settings can
only be tightened; zero, negative, sub-second, over-ceiling or idle>absolute
values are refused at construction and the SQLite `CHECK`s independently refuse
them. Freshness uses the server clock: age exactly 15 min is fresh, 15 min+1 s
needs step-up; future authentication time is treated as clock uncertainty.

## Required-assurance floor (NIST E03, E09, E12, I08, D-04)

Two different questions were once answered by one number, which let a protective
report or an exhausted factor *lower* an account's gate. They are now separate:

* **Required assurance (the floor)** - what a "max available" sensitive write
  demands. `assuranceFloor(control, user, admin, authenticators)` is 2 for
  administrators and any non-`optional` MFA policy; otherwise 2 as soon as the
  account has **ever bound** a TOTP/WebAuthn factor of the current credential
  generation, unless every such factor was **deliberately retired**. Live,
  disabled, retry-exhausted, expired, protectively invalidated and pre-migration
  ambiguous factors all keep it at 2. `SessionInfo.RequiredAssurance`; the only
  value `RequireSensitive` gates on. Unset/out-of-range is denied, never defaulted.
* **Usable assurance (capability)** - 2 only when a currently usable second factor
  exists. `SessionInfo.UsableAssurance`, informational only: it chooses between
  "step up" (`step_up_required`) and "no way to meet it" (`assurance_unavailable`)
  and is never permission to downgrade. (`MaxAssurance` was removed because it
  conflated the two; `/session` now reports `required_assurance` and
  `usable_assurance`.)

The same floor decides login issuance, `RequireSensitive`, step-up and
`freshSession`. A lower-assurance (password-only) session is **issued** only where
policy allows it **and** (floor < 2 or a usable second factor exists to step up
with). Consequently a password-only compromise report that removes the last
usable factor of an AAL2-capable optional-MFA account yields **no** new normal
session and no preauth capability: the way back is the already-approved restricted
recovery (password + saved code, then a proven replacement factor). A genuine
AAL1-only account, and an account that deliberately removed its factors with fresh
maximum assurance, keep the approved password-only behaviour.

**Issuance rule, not a verification rule (C2 parity).** The "no stranded
password-only session" test is applied only when a session is issued
(`PasswordLogin`, `LoginWithoutMFA`). `Authenticate` does **not** re-apply it, so a
legitimately issued skip-MFA AAL1 session is accepted or rejected by
`Sessions.Authenticate` exactly as by the shared authorizer verifier
(`authz.VerifyPrincipal`, used for both authorization and decision revalidation)
after the account's factor later becomes exhausted, expired or retired
(`TestSkipMFASessionParityAfterFactorBecomesUnusable`,
`TestSkipMFASessionParityAfterRealRetryCeilingCrossing`). Such a session never
gains authority: while the floor is 2 every sensitive class returns
`assurance_unavailable` and the lifecycle writes deny. Protective reports and
factor removal still revoke the sessions that depend on the affected factor.

Known consequence (reviewer note L4, accepted as the conservative rule): a fresh
AAL2 removal of an account's last live factor while a protectively reported
sibling still exists is recorded `authorized_removal`, but the protective sibling
keeps the floor at 2, so the account has no password-only session afterwards and
uses the approved restricted recovery (saved codes). Operators should remove or
recover the reported sibling first; no self-service shortcut is added.

### Retirement provenance (migration 00010)

`authenticators.retirement_reason` is NULL or one of:

| Value | Written by (same statement as the revocation) | Lowers the floor |
| --- | --- | --- |
| `protective` | `reportCompromise` (TOTP and WebAuthn; password-only evidence) | no |
| `authorized_removal` | `RevokeTOTP`, `WebAuthnService.Revoke` after `freshSession` (fresh maximum-assurance proof) | yes |
| `recovery_replacement` | approved restricted recovery that bound a verified replacement (`ConfirmRecoveredTOTP`, WebAuthn recovered registration) | yes |
| NULL on a revoked row | every revocation recorded **before** this migration | no - kept conservatively |

Rules enforced in SQLite, not only in Go: provenance exists only on a revoked
`totp`/`webauthn` row; it is write-once; the only change allowed is
`protective` -> `recovery_replacement`; and a NULL (ambiguous) record can never be
backfilled into `protective` or `authorized_removal`. Retry-ceiling suspension is
not a retirement (the row stays `disabled`, no reason written). Notice events,
their timestamps, delivery or retention are never consulted.

**Migration semantics.** `00010` only adds the column and triggers; it does not
update any row. A pre-existing revoked second factor therefore stays ambiguous and
keeps the floor at 2. **Documented consequence:** an optional-MFA account that
removed its last factor before this migration (or whose factor was revoked by any
earlier path) cannot obtain a password-only session or password-only
authenticator/password change until it completes approved recovery; recovery then
settles the ambiguous rows to `recovery_replacement` in the same transaction that
activates the verified replacement and consumes the capability. If that
transaction fails, none of it commits. `Down` drops the column; it should not be
used on a database that already holds provenance, because the floor would then
forget it (this is the same posture as every other additive column).

## Sensitive operations (TD §4.3)

`RoutePolicy.Sensitive` requires one of the declared classes and an **unsafe**
method (POST/PUT/PATCH/DELETE): safe methods skip Origin and CSRF by design, so a
sensitive class on `GET` is refused at registration. An undeclared class is
refused at registration and `RequireSensitive` denies it. **`aal2`** classes
need AAL2 evidence outright; the others need the account's *required-assurance
floor* (NIST E03): a genuinely AAL1-only account re-verifies its password, an
account that is or was AAL2-capable (and has not deliberately retired its
factors) never can with a password alone.

| Class | Needs | Current implementers / future owner |
| --- | --- | --- |
| `password-change` | floor, ≤15 min | `Service.ReplacePassword` primitive; P1.16 adapter |
| `authenticator-change` | floor, ≤15 min | `BeginTOTP/ConfirmTOTP/RevokeTOTP`, `IssueRecoveryCodes`, WebAuthn `Begin/FinishRegistration/Revoke` (each re-checks freshness itself via `freshSession`) |
| `notification-address-change` | floor, ≤15 min | `RetryNotice` repair; address ceremony P1.16 |
| `agent-credential-change` | AAL2, ≤15 min | `AdminHTTP` credential/disable routes and `Admin` service (P1.10, [contract](agent-credentials.md)) |
| `backup-export`, `backup-restore` | AAL2, ≤15 min | P1.18 |
| `security-policy-change` | AAL2, ≤15 min | user/group/agent/membership administration (P1.10); policy rules P1.11/P1.17 |

The protective **compromise report** is deliberately *not* a session step-up
class: per NIST E12 it is authorized by the password plus bound-factor protocol in
`Lifecycle`/`WebAuthnService`, grants no replacement, session or admin authority,
and revokes the user's sessions.

## Browser boundary

* **Cookie** `__Host-mandatary_session`: `Secure; HttpOnly; SameSite=Strict;
  Path=/`, no `Domain`, no `Max-Age`/`Expires` (not persistent; server expiry is
  authoritative). Value = unpadded base64url of the 32-byte secret. Exactly one
  such cookie must be present (duplicates, quoting, padding, unprefixed or
  `__Secure-` look-alikes are rejected). Clearing uses `Max-Age=0` with the same
  scope.
* **Origin**: every POST/PUT/PATCH/DELETE needs exactly one `Origin` equal to the
  configured HTTPS origin (no `null`, subdomain, port, scheme, userinfo, case or
  trailing-slash variants) and `Sec-Fetch-Site` absent or `same-origin`.
* **CSRF**: unsafe session/preauth routes also need `X-CSRF-Token` equal to
  `HMAC-SHA256(secret, id)`; per-session, rotates with the secret, header-only.
  Anonymous unsafe routes (first login step) are Origin/content-type protected.
* **Content type**: a request with a body must be `application/json` (optional
  `charset=utf-8`), so simple form/text posts cannot reach handlers.
* **Host**: must equal the configured origin host. `X-Forwarded-*`, `Forwarded`,
  `Authorization`, `_method` and method-override headers are never trusted.
* **Routes**: only method-qualified patterns with an explicit `RoutePolicy`
  (zero value invalid). A Sensitive class on a GET route, and Sensitive/Background
  combinations that weaken policy, and duplicate registrations are refused.
* **Responses** (every response including 404/405/421): `Content-Security-Policy:
  default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action
  'none'`, `X-Content-Type-Options`, `Referrer-Policy: no-referrer`,
  `Cache-Control: no-store`, `X-Frame-Options: DENY`, COOP/CORP same-origin,
  HSTS (no `includeSubDomains`). The SPA document keeps its own strict static
  policy; a CORS preflight never receives CORS headers.
* **Failure mapping**: 401 `unauthenticated` (cookie cleared if one was
  presented), 403 `forbidden` / `step_up_required` / `assurance_unavailable`,
  415, 421, 503 `unavailable` for storage uncertainty. Storage faults never
  authenticate.
* **Secrets**: `Session`, `IssuedSession` and `SessionInfo` formatting/logging
  redact secrets; canary tests cover both log formats at all four levels.

## Remaining boundaries and risks (not resolved here)

* **No claim** of AAL2 conformance, NIST/FIPS certification, browser matrix or
  runtime support. Real browser behaviour of `__Host-`/`SameSite=Strict`, WebAuthn
  UI and password-manager flows is P1.16/20 evidence.
* TLS: `Secure` cookies require HTTPS; this code trusts no forwarded protocol and
  cannot prove the proxy→app hop is protected (D-06). P1.19 documents/tests the
  topology; an untrusted cleartext hop would make the Secure cookie meaningless.
* Session rows are retained after expiry/revocation (they are referenced by
  challenge and binding foreign keys). The bounded retention/deletion policy is
  part of the P1.19/20 governance evidence (A08/D-09); live rows per user are
  bounded now.
* `SameSite=Strict` means a top-level navigation from another site arrives
  without the cookie and the SPA must re-request session state; this is a
  deliberate defence-in-depth choice.
* CSRF token and cookie rotate at step-up; a second tab holding the old token gets
  403 and must re-read session info.
* Pending TOTP/WebAuthn ceremonies started under a predecessor session do not
  survive a step-up.
* The per-IP traffic gate is the one already in `Service`/`Lifecycle`; its shared
  NAT and IPv6 caveats from the password contract still apply.
